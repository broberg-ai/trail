# F201.8 — Per-KB auto-approval for ambient captures

> The payoff of F201.11: now that ambient candidates are distilled to clean
> knowledge, a KB can opt in to auto-approving them — high-confidence knowledge
> becomes a Neuron with no click, noise stays pending. The queue becomes a
> reversible ledger, not a blocking inbox. Per-KB, not Trail-wide.

## Motivation

Ambient capture is high-volume; hand-approving every candidate is exactly the
"boring manual work" the feature exists to remove. F201.11 made auto-approval
*safe* (candidates are clean, noise is flagged conf 0). This story wires the
auto-approval so a personal ambient KB fills itself.

Christian's framing (2026-07-02): a curator judging whether what he does is
"RIGHT" is illusory — for a personal ambient KB the bar is different. But
curation stays Trail's value for Sanne/customers, so this is **per-KB**, default
OFF.

## The key obstacle (why this isn't just "set a threshold")

The existing auto-approval policy (F19) has `if (candidate.createdBy) return
false` — humans never auto-approve. Ambient candidates are POSTed via the
device-auth token, whose actor is a user, so `createdBy` is set → they were
blocked even at confidence 1.00 (observed: conf-1.00 captures stayed pending).

An ambient capture is a **machine** capture — the agent + distill decided
what's knowledge; the user never clicked "submit". So the createdBy rule (which
guards a curator's own submit-click) shouldn't apply to it. F201.8's core move:
ambient candidates **bypass** the createdBy block when the KB opts in.

## Design

- **Schema** (migration 0041): `knowledge_bases.auto_approve_threshold` (real,
  nullable, default NULL). NULL = OFF (ship-dark). A number in [0,1] arms it.
- **Policy** (`shouldAutoApprove(candidate, kb?)`): evaluated FIRST, before the
  createdBy block — if `kb.autoApproveThreshold != null` AND the candidate is
  ambient (`metadata.connector = trail-ambient-capture`) AND `confidence >=
  threshold` → auto-approve. Everything else is unchanged (kb omitted →
  threshold null → original logic, no regression).
- **Call site** (`candidates.ts` enqueue): load the KB's threshold, pass it in.
- **API** (`PATCH /knowledge-bases/:id`): accept `autoApproveThreshold`
  (null clears, [0,1] sets).
- **Admin UI**: a per-KB control in KB Settings (mirrors the F200.1 lint
  toggle), with `data-testid`, Lens-verified.

With the F201.11 distill setting knowledge=0.8 / noise=0, a threshold of e.g.
0.5 cleanly separates: distilled knowledge auto-approves, noise stays pending.

## Non-Goals

- NOT Trail-wide — per-KB, default OFF. Sanne's KB is unaffected.
- NOT changing behaviour for non-ambient candidates (chat-answer, curator,
  ingest) — they keep the existing createdBy + global-threshold logic.
- NOT auto-approving noise — a noise verdict is conf 0, below any sane
  threshold, so it never auto-approves.

## Rollout

Deploy engine (migration runs on boot). Enable on the ambient-test KB
(`PATCH … {autoApproveThreshold: 0.5}`) and confirm a fresh distilled capture
becomes a Neuron with no click, while a noise capture stays pending. Roll to a
real personal KB once trusted.

## Acceptance criteria

1. Migration adds the per-KB threshold column; round-trip read/write proven.
2. A candidate above threshold auto-approves → Neuron with no manual action; one
   below stays pending — both proven by a scripted probe.
3. Admin Settings UI exposes the threshold per KB with data-testid, Lens-verified.
4. Ship-dark: default (NULL) reproduces existing behaviour — no regression.
