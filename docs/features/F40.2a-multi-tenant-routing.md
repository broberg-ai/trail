# F40.2a — Multi-tenant routing (engine-side, flag-gated)

**Status:** Planned · **Parent:** [F40 — Multi-tenancy](./F40-multi-tenancy.md) · **Owner:** trail-server · **Depends on:** F40.1 (libSQL driver, shipped) · **Unblocks:** broberg.ai tenant on engine-001, F36 (docs.trailmem.com), F38 (cross-Trail chat)

## TL;DR

The smallest possible slice of [F40.2](./F40-multi-tenancy.md) that turns
`trail-engine-001` from "one tenant per process" into "N tenants per
process". Just the routing layer: a key→tenant index, a DB-pool keyed
by tenant slug, an auth-middleware change that resolves the right DB
per request, and a refactor of the background-services boot loop so
every tenant gets the same job treatment.

**Explicit non-goals (deferred to F40.2b+):** provisioning UI,
deprovisioning, tier upgrade Pro→Business, dev-mode fallback for the
local Mac flow. Those layer cleanly on top once routing works.

**Critical constraint:** Sanne's `t-sanne-andersen` API output must be
**byte-for-byte identical** before and after this lands. She is days
from release. The whole change is gated behind a feature flag
(`TRAIL_MULTI_TENANT=1`); with the flag off, the engine runs exactly
like today.

## Motivation

Right now `trail-engine-001` has `TRAIL_DB_PATH=/data/sanne-andersen/trail.db`
in its Fly env and `apps/server/src/index.ts` opens that one DB at
boot. Christian provisioned a `broberg-ai` tenant on the same volume
2026-05-20 (control.db + `/data/broberg-ai/trail.db` + bearer key) —
but engine-001 never opens that file, so the bearer lookup misses
and broberg.ai gets 401.

Two paths were considered (May 20 discussion):

- **A**: deploy `trail-engine-002` as a second single-tenant Fly app.
  Avoids any engine-code change, but requires either DNS-level
  routing or a baby-F170 router for `engine.trailmem.com` to point at
  both. Effectively the same complexity as doing routing properly,
  spread across more apps.
- **B**: implement F40.2 routing inside engine-001. Each engine process
  serves N tenants. Doesn't need F170 until fleet actually grows.

Christian chose B. This plan-doc is the implementation contract for B.

## Scope (in)

### 1. Central key→tenant index

A single small SQLite file `/data/key-index.db` holds the
**only** mapping that an engine consults pre-request:

```sql
CREATE TABLE api_key_index (
  key_hash TEXT PRIMARY KEY,         -- sha256(bearer)
  tenant_slug TEXT NOT NULL,         -- e.g. 'sanne-andersen'
  user_id TEXT NOT NULL,             -- denormalised for fast auth
  created_at TEXT NOT NULL,
  revoked_at TEXT                    -- soft-delete; NULL = active
);
CREATE INDEX idx_api_key_index_slug ON api_key_index (tenant_slug);
```

`session_index` follows the same shape for cookie-based magic-link
sessions:

```sql
CREATE TABLE session_index (
  session_id TEXT PRIMARY KEY,
  tenant_slug TEXT NOT NULL,
  user_id TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  created_at TEXT NOT NULL
);
```

Both are **denormalised projections** of the per-tenant `api_keys` and
`sessions` tables. Source-of-truth stays in the tenant DBs; the index
exists purely to make pre-DB-open auth lookups O(1).

Writes to the index happen at two points:

- **Bearer creation** (admin/UI flow): when a tenant creates an API
  key, the create-handler INSERTs into both that tenant's
  `api_keys` AND the global `key_index`.
- **Session creation** (auth/me, magic-link redeem): same — both
  the tenant's `sessions` table AND the global `session_index`.

A drift-detector at boot reconciles indexes against tenant DBs (paint
any newly added bearers/sessions that didn't make it to the index
during a partial-failure window).

### 2. DB-pool keyed by tenant slug

Replace the single `const trail = await createLibsqlDatabase(...)` at
boot with a pool:

```ts
type TenantPool = Map<string /* slug */, TrailDatabase>;

async function openTenantPool(): Promise<TenantPool> {
  const pool: TenantPool = new Map();
  for (const slug of discoverTenantSlugs('/data')) {
    const db = await createLibsqlDatabase({ path: `/data/${slug}/trail.db` });
    await db.runMigrations();
    pool.set(slug, db);
  }
  return pool;
}
```

`discoverTenantSlugs` walks `/data/*` looking for directories that
contain a `trail.db` and that are NOT in the exclude-list
(`_archive`, `_incoming`, `backups`, `lost+found`, `uploads`).

The pool is read-only after boot (Phase 1). Adding a new tenant at
runtime is a Phase 1b concern (F40.2b — provisioning).

### 3. Auth-middleware: bearer/session → tenant resolution

Refactored `apps/server/src/middleware/auth.ts`:

```
authHeader: 'Bearer trail_…'  →  hash  →  key_index.get(hash)
                              →  { tenant_slug, user_id }
                              →  pool.get(tenant_slug)
                              →  c.set('trail', db); c.set('user', {…}); c.set('tenant', {…})

session cookie: 'sess_…'      →  session_index.get(id)
                              →  { tenant_slug, user_id, expires_at }
                              →  pool.get(tenant_slug)
                              →  c.set('trail', db); …
```

If either lookup misses or the pool has no handle: **401, no
fallback, no iteration over DBs**. This is the security-critical part
Christian was emphatic about. There is **never** a code path that
tries multiple DBs looking for a match.

The downstream handler code is unchanged. It still reads `trail =
c.get('trail')` and works against whichever DB the middleware
selected.

### 4. Background services iterate over pool

Today these services run with `trail` bound to the boot-time global:

- `lint-scheduler` — F118 contradiction-lint, F158 signature-skip
- `contradiction-lint` (reactive)
- `reference-extractor`, `backlink-extractor` (F137)
- `link-checker` (F156)
- `action-recommender` (F140)
- `activity-logger` (F141)
- `upload-session-gc`
- `queue-backfill`
- F164 `jobs/runner`

Each becomes:

```ts
for (const [slug, trail] of pool) {
  await scheduledTaskFor(slug, trail);
}
```

Bootstrap-time one-shots (ensureIngestUser, recoverZombieIngests,
rewriteWikiToNeurons, cleanupExternalOrphans, seedMissingGlossaryNeurons,
recoverPendingSources, backfillContentHash, backfillDocumentImages,
rerunVisionOnNull, sweepAutoFlag, seedDevCreditsOnBoot) — same pattern,
just an outer loop over the pool.

Every tenant gets the full job treatment. No second-class tenants.

### 5. Feature flag rollout

The new code path is fully gated:

```ts
const MULTI_TENANT = process.env.TRAIL_MULTI_TENANT === '1';

if (MULTI_TENANT) {
  // open pool, set up multi-tenant middleware,
  // iterate background services over pool
} else {
  // existing single-tenant path: open DEFAULT_DB_PATH only,
  // legacy auth-middleware, single-tenant background services
}
```

With the flag OFF, every existing engine boot path is preserved
identically. Deploying the F40.2a code WITHOUT setting the flag is a
silent change for Sanne — same DB opened, same middleware, same job
loop.

The flag is flipped via `flyctl secrets set TRAIL_MULTI_TENANT=1`,
which triggers an engine restart. The verify-script runs against
Sanne's endpoints both before and after the flip to confirm
byte-for-byte parity.

## Scope (out — explicit non-goals for F40.2a)

- **Provisioning UI / API** — adding a new tenant still requires
  manual creation of the directory + DB + index rows. F40.2b will
  add admin endpoints for tenant CRUD.
- **Deprovisioning** — same, F40.2b.
- **Tier upgrade Pro → Business** — F40.2b.
- **Dev-mode fallback** — the local Mac engine on port :58021 stays
  single-tenant for now (uses TRAIL_DB_PATH like today). F40.2b will
  unify the dev story.
- **F170 router / inter-engine** — out of scope, separate feature
  for when fleet actually grows past one engine app.
- **Schema changes to tenant DBs** — none. F40.2a only adds a NEW
  `key-index.db` file. Sanne's `trail.db` schema is untouched.

## Architecture

```
┌─────────────────────────── trail-engine-001 (Fly machine) ───────────────────────────┐
│                                                                                       │
│   Boot:                                                                               │
│     - open /data/key-index.db                                                         │
│     - discover /data/<slug>/trail.db files                                            │
│     - open pool: { 'sanne-andersen' → DB1, 'broberg-ai' → DB2 }                       │
│     - run drizzle migrations against each (idempotent)                                │
│     - run bootstrap one-shots for each (ensureIngestUser, …)                          │
│     - start background services as `for (const [slug,db] of pool) startServiceFor()`  │
│                                                                                       │
│   Per request:                                                                        │
│     ┌─ middleware/auth.ts ─────────────────────────────────────────┐                  │
│     │  bearer?                                                     │                  │
│     │    hash → key_index.get(hash)                                │                  │
│     │      → { tenant_slug, user_id }                              │                  │
│     │      → c.set('trail', pool.get(tenant_slug))                 │                  │
│     │      → c.set('user', {…}); c.set('tenant', {…})              │                  │
│     │  session cookie?                                             │                  │
│     │    session_index.get(id) → … (same)                          │                  │
│     │  miss → 401 (never iterates DBs)                             │                  │
│     └──────────────────────────────────────────────────────────────┘                  │
│                                                                                       │
│   Route handlers: unchanged. They use `c.get('trail')` and never see slug.            │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

## Test plan — Sanne byte-for-byte baseline

Before F40.2a deploy:

1. `apps/server/scripts/baseline-sanne-api.ts` — sweeps a fixed query
   set against engine-001's `engine.trailmem.com`:
   - GET `/api/v1/me` (with Sanne's session cookie)
   - POST `/api/v1/chat` with 5 canonical questions (drawn from her
     own KB so retrieval is deterministic given the same data)
   - GET `/api/v1/knowledge-bases/sanne-andersen` (KB metadata)
   - GET `/api/v1/knowledge-bases/sanne-andersen/documents?limit=10`
   - POST `/api/v1/knowledge-bases/sanne-andersen/reader-feedback`
     (F31 endpoint)

   Writes responses to `apps/server/.baseline/sanne-<endpoint>.json`
   committed under `.gitignore` exception so the file exists locally
   but isn't in the repo.

2. **Flag-off code-deploy** — `pnpm ship:engine` lands F40.2a code
   on engine-001 with `TRAIL_MULTI_TENANT` unset. Engine restarts.

3. Re-run baseline → diff against pre-deploy capture. **Must match
   byte-for-byte** for the non-timestamped fields. (Allow drift on
   `sessionId`, `created_at` if they're random/new — exclude via
   diff config.)

4. **Flag-on flip** — `flyctl secrets set TRAIL_MULTI_TENANT=1`,
   engine restarts.

5. Re-run baseline → must STILL match. If chat answers differ even
   for one query, abort: `flyctl secrets unset TRAIL_MULTI_TENANT`,
   engine restarts back to single-tenant. ~30s rollback.

6. Smoke test broberg-ai bearer:
   `curl -H "Authorization: Bearer $BROBERG_BEARER" engine.trailmem.com/api/v1/chat
    -d '{"knowledgeBaseId":"trail-research","message":"..."}'`
   → expect grounded answer from broberg-ai data, not Sanne's.

## Open questions

- **Q: Where exactly does `key-index.db` live?** Proposed: `/data/key-index.db`
  on the engine volume. Alternative: a small Fly-internal SQLite app
  shared across engines. For F40.2a (fleet=1) the engine-local file
  is sufficient; F170 may relocate it.
- **Q: How do we handle key-index drift in the rare partial-failure
  case?** Proposed: a startup-time reconciler that scans every tenant
  DB's `api_keys` + `sessions` and INSERTs missing rows into the
  index. Logs drift count, exits with non-zero if drift exceeds 10%
  (signal of bigger problem).
- **Q: Should the flag also gate boot behavior, or just request-time?**
  Proposed: gates both. With flag off, only `DEFAULT_DB_PATH` is
  opened — pool is not constructed. This means flipping the flag
  requires a restart, which is fine (~5s downtime).
- **Q: What's the broberg.ai bearer that we already created (key_d8ad2efc8073306b)?**
  It exists in broberg-ai's `api_keys` table but not in the
  yet-to-be-created `key_index`. Backfill script (step 3) picks it
  up automatically.

## Acceptance criteria

- [ ] `TRAIL_MULTI_TENANT=0` (or unset): engine boots identically to
  pre-F40.2a, Sanne API output byte-for-byte unchanged
- [ ] `TRAIL_MULTI_TENANT=1`: engine opens pool, both Sanne + broberg-ai
  bearers resolve to their own DB
- [ ] Sanne's bearer NEVER hits broberg-ai's DB (verified by trying
  to read a broberg-ai-only doc via Sanne's bearer → 401 or
  not-found, never accidentally returned)
- [ ] broberg-ai's bearer NEVER hits Sanne's DB (cross-test)
- [ ] Background services run on BOTH tenants — lint, contradictions,
  job-runner all touch broberg-ai data within one cycle of flag-on
- [ ] Verify-script's baseline diff is empty after flag-on
- [ ] Rollback to flag-off works in <60s
