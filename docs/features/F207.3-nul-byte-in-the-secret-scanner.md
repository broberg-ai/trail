# F207.3 — a raw NUL byte in the secret scanner

**Card:** trail-F207.3 · **Parent:** F207 (no credential reaches git) · 2 SP · critical

## Motivation

`scripts/scan-secrets.ts` is the gate F207.2 built so a credential cannot enter
git. This repo is **public**, and a full-access Trail key was readable by anyone
in it for four months. The gate is therefore load-bearing in the strongest sense.

It contains **one raw NUL byte**, at offset 3116:

```ts
if (text.includes('<a literal 0x00>')) continue; // binary
```

The behaviour is **correct today**. That is what makes it worth a card rather
than a shrug: it is one save away from being catastrophically wrong, and the
wrongness is invisible.

### The failure mode

Any formatter, linter, editor or copy-paste that strips control characters turns
the argument into the **empty string**. `text.includes('')` is `true` for every
string. So:

1. every file hits `continue`;
2. `hits` stays empty;
3. the run prints `[secret-scan] clean — 412 file(s) scanned`;
4. it exits **0**, and both the pre-commit hook and CI go green.

A security control that has stopped working, reporting a pass, with a plausible
file count attached to make it convincing. Nobody would look again.

### Why nobody had noticed

A NUL byte makes a file **invisible to grep**. The harness grep is ugrep with
`-I`, which silently skips NUL-containing files. `grep -nE "exit|length|staged"`
over a 4,178-byte file returns nothing, with no error and no warning. Every
session that has ever audited this scanner got an empty result and read it as
"nothing to see".

The peer who found it (components, 2026-09-01) could only read the file by going
around grep with node.

## Two more defects in the same file, found by the same read

**Coverage was never reported.** `if (hits.length === 0)` declared the tree clean
without regard to how many files were actually read. A run that scanned *nothing*
printed `clean — 0 file(s) scanned` and exited 0. The likeliest cause of an empty
file list is a wrong working directory — i.e. exactly the situation in which a
confident all-clear is most wrong.

**Unreadable files vanished.** `catch { continue }` dropped them silently and
uncounted, so the tool's own output could not tell you what it had missed.

## The family this belongs to

*One signal, two facts.* "Nothing was found" and "nothing was looked at" arrived
as the identical sentence. The repo has now met this shape five times in a week:

| Instance | The signal | The two facts it could not separate |
|---|---|---|
| F212.4 | `rejected: 0` | nothing matched / not allowed to say |
| F214.2 | 200 + a full page | next page / the same page again |
| `@broberg/secret-scan` | `findings: []` | text is clean / that axis was never checked |
| buddy's env audit | "15 lines starting with `TRAIL_`" | the three specific vars are set / some are |
| **F207.3** | `clean — N scanned` | nothing to find / nothing was read |

## Scope

**In:**
- Replace the literal byte with the `'\0'` escape.
- Count `scanned`, `skipped` (binary) and `unreadable`, and print all three.
- A run that matched files but read none **exits 1**.

**Non-goals:**
- Not changing what counts as a secret — detection lives in `@broberg/secret-scan`
  and is not this card's business.
- Not removing the binary skip. Binary files *should* be skipped; they must just
  be counted rather than invisible.
- Not adopting `@broberg/greppable` here. components offered it as the tool that
  would have named this file, and they are right that we run zero `@broberg/*`
  packages — but a fleet-wide adoption is Christian's call, not a side effect of
  a security fix. Raised separately.

## Verification

The negative control is the whole point. A scanner that exits 0 on a clean tree
proves nothing unless it also exits 1 on a dirty one.

1. Read the file as a **Buffer** and count `0x00` → must be 0. Not with grep,
   which is structurally unable to see the thing being asserted.
2. Build a fixture containing a **real** NUL byte and confirm it is skipped and
   counted as binary.
3. Plant a credential in a **staged** file and confirm the scanner exits non-zero
   and names it. (First attempt at this used an *untracked* file and the scan
   passed — the scanner reads tracked files, so the control was measuring
   nothing. Recorded because that near-miss is the same class of error as the
   bug.)
4. Drive it at a set it cannot read → exit 1, message says so.
5. **Mutation:** restore the empty-string argument, i.e. the post-formatter
   state, and assertion 2 must go red.

## Credit, and the part worth keeping

components found this. They also reported that **our own hook comment** — *"Fail
loudly rather than pretending the check ran. A silent skip is exactly how a key
stayed in this public repo for four months"* — is what made them re-read line 67
of their own hook, where they had the identical defect and shipped a fix the same
day.

The lesson was already written down in this repo, in the right words, and had
never crossed the boundary to the repo that needed it. That is worth more than
the fix.
