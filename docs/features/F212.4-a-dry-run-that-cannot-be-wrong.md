# F212.4 — The lint-drain dry-run always answers 0

**Status:** backlog · **Parent:** [F212](F212-silent-failure-guards.md) · **Found:** 2026-08-29, running buddy's F200.2 daily drain · **Confirmed by:** the buddy session

## What was measured

Buddy dispatched the daily lint-drain against `broberg-ai`. Run twice, seconds
apart, against production:

```
apply:false → {scanned: 0, rejected: 0, disabledKbs: 3, applied: false}
apply:true  → {scanned: 0, rejected: 0, disabledKbs: 3, applied: true}
```

Identical apart from the `applied` echo. So the dry-run told me nothing:
**"there was nothing to drain" and "the preview never counts" are the same
screen.**

The only honest reading of that 0 came from a DIFFERENT endpoint — counting the
queue afterwards: 41 pending, 40 `external-feed` + 1 `ingest-summary`, no lint
candidates among them. An answer you can only trust by measuring something else
is not an answer.

## Why it belongs under F212

This epic exists because three failures ran silently for months, each invisible
because the thing that would have reported it was itself broken. Same shape,
smaller blast radius: the instrument reports success-looking numbers regardless
of what it did.

Buddy stated the cost better than I had:

> Som det står nu er tørkørslen ikke bare unyttig — den er AKTIVT VILDLEDENDE,
> fordi den ligner et svar. En knap der altid siger 0 lærer folk at 0 betyder
> "intet at gøre", og så tror de også på det den dag der er 454.

That number is not hypothetical. This queue held **454** lint findings the day
before, drained on the owner's order. A dry-run against that state would have
answered 0 with exactly the same confidence it answers 0 today.

And it is the expensive variant of the week's recurring shape — one signal, two
facts — because the defect is in the **measuring instrument**. It does not only
corrupt its own answer; it corrupts every answer read through it, including the
future ones that would otherwise have been fine.

## Fix

`POST /api/v1/maintenance/drain-lint-candidates` in `apps/server`. The scan and
the write are one pass gated on `apply`. Split them: always scan and count,
write only when `apply` is true.

- `scanned` — candidates examined. Both modes, always.
- `rejected` — with `apply:false`, how many WOULD be rejected; with
  `apply:true`, how many were. The same number for the same state, which is the
  whole point of a preview.

## Non-goals

- Changing WHICH candidates are drained. The `lint-disabled-kbs` scope is
  correct and stays; a candidate in a lint-ENABLED KB must be untouched by both
  modes, and AC3 asserts exactly that.
- Auditing the other maintenance endpoints for the same flaw. If they share it
  they get their own cards — measured, not assumed from this one.

## Note for whoever picks this up

**Do not verify this by running it against production and reading the numbers.**
That is precisely how the bug survived: the numbers looked plausible. Build a
fixture with candidates in BOTH a lint-disabled and a lint-enabled KB, and
assert the dry-run's numbers against the apply run's — the two must agree, and
the database must change only in the second case.
