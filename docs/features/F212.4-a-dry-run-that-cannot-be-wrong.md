# F212.4 — The lint-drain preview reported 0 no matter what

**Status:** shipped · **Parent:** [F212](F212-silent-failure-guards.md) · **Found:** 2026-08-29, running buddy's F200.2 daily drain

## Correction: the first version of this plan was half wrong

It said the dry-run *never looked* — that `scanned` was gated on `apply`. **That
was not true, and it is worth leaving on the record rather than quietly
rewriting**, because getting it wrong is the same mistake the card is about.

What I actually had was two production runs answering identically:

```
apply:false → {scanned: 0, rejected: 0, disabledKbs: 3, applied: false}
apply:true  → {scanned: 0, rejected: 0, disabledKbs: 3, applied: true}
```

From that I concluded the instrument was blind. But an empty queue produces
exactly the same two lines as a blind instrument — so those runs could not tell
the two apart, **and neither could I**. I diagnosed from a measurement with no
discriminating power, told the buddy session, and they agreed. Two sessions
agreeing does not make a reading discriminate.

Reading the code said otherwise: `matching` is computed *before* the
`if (apply)` branch, so `scanned` always reflects reality. A fixture with three
real candidates settled it in one run:

```
scanned: 3   ← counted correctly all along
rejected: 0  ← the actual defect
```

## The real defect

`rejected` was hard-zero unless applying. That is the field a reader takes as
*"how many are going"*, so in preview mode **"nothing matched" and "I am not
allowed to tell you" arrived as the same answer.** The one number a preview
exists to provide was the one it withheld.

Buddy's framing of the cost stands, and it is why this was worth fixing rather
than documenting:

> Som det står nu er tørkørslen ikke bare unyttig — den er AKTIVT VILDLEDENDE,
> fordi den ligner et svar. En knap der altid siger 0 lærer folk at 0 betyder
> "intet at gøre", og så tror de også på det den dag der er 454.

That 454 is not hypothetical: it is what this queue held two days earlier.

## The fix

`POST /api/v1/maintenance/drain-lint-candidates` in `apps/server`. One line of
behaviour: `rejected` is now `matching.length` in both modes — how many *would*
be rejected when previewing, how many *were* when applying. The write stays
gated on `apply`; only the reporting changed.

## Proof

`apps/server/scripts/verify-f212-4.ts`, 11 assertions, on a fixture holding
three drainable candidates plus two that must survive (a lint finding in a
lint-ENABLED KB, and a knowledge candidate in the same KB as the drainable
ones).

The load-bearing assertion is that **the dry run's numbers are asserted against
the apply run's**, not against constants I typed — two implementations both
matching my list would still be two implementations. And every status is read
back with raw SQL, never through the layer that wrote it.

Mutation-proven, three ways, each reddening a different count:

| mutation | red |
|---|---|
| re-gate `rejected` on `apply` (the old behaviour) | 2 |
| remove the write, keep the report | 3 |
| remove the lint-disabled-KB scope filter | 4 |

The third is there because the dangerous version of this fix is one that makes
the preview honest by widening what it drains.

## Non-goals

- Changing WHICH candidates are drained. The `lint-disabled-kbs` scope is
  correct and untouched; a lint finding in a curated, lint-ON KB must survive
  both modes, and mutation C exists to prove that assertion can fail.
- Auditing the other maintenance endpoints for the same shape. If they share it
  they get their own card — measured, not assumed from this one.

## The lesson worth keeping

Before reporting a diagnosis, ask what a **negative control** would look like.
Here it was one line: *put something in the queue and run the preview again.*
That would have taken thirty seconds and would have contradicted me. Instead the
wrong diagnosis reached a peer session, was agreed with, and became a card.
