# F210.5 — A provisioned tenant must be REACHABLE, not merely present

**Status:** in progress · **Priority:** critical · **Opened:** 2026-08-28
**Reported by:** the owner, in the product, minutes after creating his first
customer tenant on production.

## What he saw

`app.trailmem.com`, tenant switcher set to **FD Aalborg**:

```
Something went wrong.
Invalid or revoked API key
```

The tenant he had just created with the brand-new `+ NEW TENANT` button could
not be opened at all.

## What was actually true

Measured on the engine before changing anything:

```
/data dirs: sanne-andersen, broberg-ai, fd-aalborg, key-index.db, …
/data/fd-aalborg/trail.db exists: true   tables: 44
api_keys rows: []
tenants  rows: []
```

Everything F210.2 promised had happened. The directory was created, the
database was migrated to all 44 tables, the endpoint answered 201, and the
tenant was hot-added to the pool without a restart. **And it was empty.**

Meanwhile the control plane had minted a bearer — *after* the successful
provision — and stored it in `tenant_engines.bearer` in `control.db`. The
engine had never heard of that key. So the proxy forwarded a real bearer to a
real database that contained no `api_keys` row to match it, and auth answered
the only thing it could.

**A tenant that exists and cannot be reached is worse than one that failed to
create.** A failed create is visible immediately, at the moment and the place
you did it. This one reported success, and surfaced later, somewhere else,
looking like an auth problem.

## Root cause

`provisionTenant()` took `{pool, slug, boot}`. `boot` migrates. Nothing wrote
rows. The three rows a request needs to resolve were never inserted:

| table | why a request needs it |
|---|---|
| `tenants` | what the slug points at |
| `users` | `api_keys.user_id` is NOT NULL and references it |
| `api_keys` | the sha256 auth compares the presented bearer against |

Plus one row in `/data/key-index.db`, the cross-tenant index auth reads FIRST
to decide *which database to open at all*.

## The second bug, found while writing the test

`addBearer()` is a **silent no-op when the index file is missing** — by
design, because single-tenant local dev legitimately has no index. But that
index is created by a one-off script (`apps/server/scripts/build-key-index.ts`)
and never at boot. So on a host where nobody had run that script, a newly
provisioned tenant would be unreachable and **nothing anywhere would say so**.

That is the same failure shape as the first bug, one layer down: a write that
cannot fail, guarding the one thing that must not be missing.

Provisioning now **reads the bearer back out of the index** and throws if it
did not land. `undefined` (no index file at all) stays legal, because a
single-tenant host does not consult it — so the check distinguishes "this host
does not use an index" from "the write did not work", which are different
facts that previously looked identical.

## The fix

**Control plane** (`apps/admin-server/src/tenants.ts`) mints the bearer
**before** calling the engine and sends its SHA-256 with the request:

```
POST /api/admin/tenants  { slug, name, ownerEmail, keyHash }
```

Only the hash crosses the wire. The engine stores hashes and nothing else, so
the raw key has no reason to travel.

**Engine** refuses the call without `keyHash` + `ownerEmail` (400) rather than
creating something unreachable, and `provisionTenant` gains a `seed` step that
runs **after** migrations and **before** the pool insert — so a tenant only
goes live once it can answer. `apps/server/src/bootstrap/seed-tenant.ts` writes
the three rows and the index entry, all insert-if-absent so a retry after a
partial failure completes rather than throwing on a row it already wrote.

## Scope

### In scope

- Provisioning produces a tenant that answers on its first request.
- Loud failure when the key index does not accept the bearer.
- `apps/server/scripts/verify-f210-5.ts` — proves reachability, not existence.

### Explicit non-goals

- **Repairing the existing `fd-aalborg` is NOT the fix.** The owner said it
  plainly: *"Det skal selvfølgelig virke ved oprettelsen af den NÆSTE tenant."*
  The repair is a separate, one-off step that uses the fixed path; a hand-patched
  row would have hidden the bug for the next customer.
- **Not** creating the key index automatically at boot. It is worth doing and it
  is a different decision (it changes what a fresh single-tenant host becomes);
  this card makes its absence *loud* rather than silently fatal.
- **Not** RBAC, plans, or engine selection — F210's non-goals stand.

## Verification

```
[exists] the part that ALREADY worked, kept as a control
  ✓ the database file was created
  ✓ and the tenant is live in the pool without a restart
[reachable] the part that did not — every row a request needs
  ✓ exactly one tenant row · slug is fd-aalborg
  ✓ the owner has a user row
  ✓ exactly one api_key row · it is the hash of the forwarded bearer · not revoked
[index] auth reads the cross-tenant index FIRST
  ✓ the key is registered, pointing at THIS tenant
[negative control]
  ✓ a key nobody minted has no index row
```

The two `[exists]` assertions are kept deliberately: under the mutation that
skips the seed they stay **green** while the eight reachability assertions go
red. That is the whole point — the old code passed "was it created" perfectly,
and a suite that only asked that question would have shipped this bug twice.

Mutation B (index write removed) makes provisioning throw by name.
