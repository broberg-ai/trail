# F165.1 — Vision derivatives (WebP) + strict-availability fallback

**Status:** Planned · **Phase:** 1 · **Owner:** trail-server · **Parent:** F165

## TL;DR

Trail's Vision pipeline is pinned to Anthropic-direct as primary (F164
Phase 3). Anthropic's Messages API rejects images > 5 MB. Phone photos
and high-res scans regularly cross that line, so vision_description
silently stays NULL and the image lands in the "mangler beskrivelse"
filter for no good reason.

F165.1 adds **vision derivatives**: a WebP-encoded, dimension-capped
copy of every image is generated alongside the original; the Vision
backend reads the derivative; the original stays untouched in storage.
Trail is becoming the customer's **Brand Intelligence Base** — losing
original fidelity on ingest is not acceptable. Generating a derivative
is.

While we're in there, F165.1 also tightens F164 Phase 3's fallback
semantics: OpenRouter fallback fires **only** on availability failures
(5xx, timeout, connection-reset). 4xx responses (including 413
"image too large") are bugs, not availability problems, and must not
be silently routed to a slower/different model.

## Motivation — what goes wrong today

- A patient-photo upload to Sanne's KB at 8 MB original → status='ready',
  image row exists, vision_description=NULL forever. The model never
  saw it. The "mangler beskrivelse" filter surfaces it as if Vision
  failed for an interesting reason; it didn't.
- Worse failure mode: a future bug raises 413 from Anthropic, F164
  Phase 3 sees an error and falls back to OpenRouter → describes the
  image (because OpenRouter's 20 MB cap is more generous), but slower
  and at different cost. The ops team sees "OpenRouter usage is up
  100% this week" and goes hunting for a regression in availability —
  there isn't one, it's input-shape drift. Strict-fallback prevents
  this.

## Scope (in)

1. **Storage layout**

   ```
   {tenant}/{kb}/{doc}/images/page-N-img-M.png         ← original (untouched)
   {tenant}/{kb}/{doc}/images/page-N-img-M.webp        ← vision derivative
   ```

   Same directory, suffix-only difference. Keeps the existing storage
   helpers happy; no new path conventions.

2. **Schema — migration 0026**

   ```sql
   ALTER TABLE document_images ADD COLUMN vision_derivative_path TEXT;
   ```

   Nullable. Filled when a derivative exists, NULL when (a) the
   original was already small enough to skip generation, or (b) we
   haven't generated one yet.

3. **Derivative generation — `apps/server/src/services/vision-derivative.ts`**

   ```ts
   export async function ensureDerivative(
     trail: TrailDatabase,
     imageRow: DocumentImage,
   ): Promise<{ bytes: Uint8Array; isDerivative: boolean }>;
   ```

   - If `vision_derivative_path` set + file exists in storage → return its bytes.
   - Else if original `file_size < 3 MB` AND `width*height < 4_000_000` →
     return original bytes, isDerivative=false. (Below threshold —
     Anthropic accepts it as-is, no point generating a derivative.)
   - Else → resize to `max(width, height) ≤ 1568`, encode as WebP@q=80,
     write to `{path}.webp` in storage, set
     `document_images.vision_derivative_path`, return derivative bytes.

   3 MB threshold leaves margin for base64 expansion (~33%) under
   Anthropic's 5 MB API limit. 1568 px is Anthropic's documented
   recommended max long-edge for image-understanding tasks.

4. **Library choice — `sharp`**

   Industry standard, native libvips bindings, fast. Already used
   elsewhere in the broader Webhouse ecosystem; consistent. Note:
   `sharp` requires native build; we already build native deps in
   the engine Dockerfile (sqlite vec, tree-sitter), so this is a
   non-event for the Fly image.

5. **Wire into vision-rerun handler**

   `apps/server/src/services/jobs/handlers/vision-rerun.ts` calls
   `ensureDerivative` before invoking the backend. The backend
   receives derivative bytes when applicable; it doesn't know or
   care.

6. **Wire into upload-time path (F165 vision-rerun job)**

   F165 already moved Vision to async. The first time the
   vision-rerun job runs for a freshly-ingested doc, the
   per-image loop calls `ensureDerivative` — derivative is
   generated then, not at upload time, so upload latency is
   unaffected.

7. **F164 Phase 3 fallback — strict availability semantics**

   `apps/server/src/services/vision/anthropic-backend.ts` (or wherever
   the chain lives): error classification before deciding to fall back.

   ```ts
   function shouldFallback(err: unknown): boolean {
     if (err instanceof FetchTimeout) return true;            // network timeout
     if (err instanceof FetchConnectionError) return true;    // ECONNRESET, DNS, etc.
     if (err instanceof AnthropicApiError && err.status >= 500) return true;
     return false;  // 4xx (incl. 413) → don't fallback, throw
   }
   ```

   4xx errors propagate. Vision-rerun handler catches them per-image,
   counts toward `failed`, logs the status code, and moves on. The
   curator can act on a real 4xx (e.g. the image is corrupted) instead
   of having it silently re-tried via a more expensive provider.

8. **Backfill for existing oversized images — opt-in script**

   `apps/server/scripts/backfill-vision-derivatives.ts`: scans
   `document_images WHERE vision_description IS NULL`, generates
   derivatives for any over-threshold rows, optionally re-submits a
   vision-rerun job afterward. Manual trigger; not a boot-time hook.

9. **Verify-script** —
   `apps/server/scripts/verify-f165-1-vision-derivatives.ts` proves:
   (a) under-threshold image → no derivative generated, original used;
   (b) over-threshold image → derivative written, vision_derivative_path
   set, derivative bytes returned, derivative is < 5 MB and roughly
   matches original aspect ratio;
   (c) idempotent — second call returns existing derivative without
   re-encoding;
   (d) shouldFallback unit-tested for 5xx/timeout=true,
   413/400/401/404=false.

## Scope (out / explicit non-goals)

- **Replace originals.** Originals stay byte-identical in storage
  forever. F165.1 only *adds* a sibling derivative. Brand Intelligence
  Base requirement.
- **Public-facing image serving via derivatives.** The image-serving
  endpoint (`/api/v1/documents/:docId/images/:filename`) keeps
  returning originals. Derivatives are server-internal Vision-input
  only. (Future feature could expose them as a `?variant=vision`
  query param, but not in F165.1.)
- **Multiple derivative variants** (thumb, medium, etc.) Out of scope.
  One Vision-sized derivative; nothing else.
- **Re-encoding when prompt/model changes.** Derivative is content-
  addressed by source path. If we change the prompt, we re-run Vision
  on the same derivative — quality of the derivative is independent
  of how we ask the model.
- **EXIF stripping.** WebP encoding via sharp drops EXIF by default;
  that's fine for the derivative (Vision doesn't read EXIF). The
  original retains EXIF, which is what F163.3 surfaces in the
  Lightbox.
- **Lossless WebP.** q=80 lossy is the right choice — saves ~5×
  vs lossless and produces no perceivable Vision-quality difference.
- **Tightening of `MAX_FILE_SIZE = 100 MB`** in the upload route. We
  still accept up to 100 MB originals; only Vision sees the derivative.

## Architecture sketch

### Today (post-F165, pre-F165.1)

```
upload → extract → persist images (NULL desc) → submit vision-rerun job
                                                         │
                                                         ▼
                                       for each image (pLimit 4):
                                         load original from storage
                                         backend(originalBytes)  ← 413 if > 5 MB
                                                                   silent NULL forever
```

### After F165.1

```
upload → extract → persist images (NULL desc, NULL deriv-path) → submit vision-rerun job
                                                                          │
                                                                          ▼
                                                  for each image (pLimit 4):
                                                    bytes = ensureDerivative(image)
                                                       ├─ small? → original bytes
                                                       └─ big?   → webp 1568/q80, persist path, return bytes
                                                    backend(bytes)
                                                       ├─ 5xx/timeout → fallback to OpenRouter
                                                       └─ 4xx        → throw, count as failed, log
```

### Key invariants

- **Originals are immutable.** Once written at upload time, the file
  at `images/page-N-img-M.png` is never touched again. Derivatives
  live alongside, not in place of.
- **Derivative path is content-stable.** Same source path → same
  derivative path. No timestamp salting; idempotent regeneration.
- **A derivative existing implies the original exists.** Derivative
  generation reads original bytes, so failure to load original →
  no derivative written → vision_derivative_path stays NULL.
- **Threshold check is cheap.** width/height/file_size are already
  on document_images; we don't re-stat the file just to decide.

## Dependencies

- **F165** (async vision-rerun job). Without F165, derivatives would
  have to be generated synchronously during upload, defeating F165's
  whole point. Wait — F165 already shipped, so this is just ordering.
- **F164 Phase 3** (vision provider chain). F165.1 modifies its
  fallback semantics; the chain itself stays.
- **F161** (`document_images` schema). New column attaches there.
- **`sharp`** as new runtime dep on the engine. Adds ~25 MB to the
  Docker image; acceptable.

## Rollout

- **Phase 1** (this feature, ~½ day):
  1. Migration 0026 — `vision_derivative_path` column.
  2. `vision-derivative.ts` service + sharp dep.
  3. Wire into `vision-rerun` handler.
  4. Verify-script.
  5. Tighten F164 Phase 3 fallback to availability-only.

- **Phase 2** (opt-in backfill, ~hour after Phase 1 lands):
  1. `scripts/backfill-vision-derivatives.ts` — generates derivatives
     for over-threshold images that currently have NULL
     vision_description.
  2. Manual run on Sanne's KB (where the original 5 MB-plus failures
     surfaced).

- **Phase 3** (future, not in F165.1): expose `?variant=vision` on
  the public image endpoint so external integrations can fetch the
  small derivative for their own model calls without proxying the
  original. Cost-saver for Tier 1 retrieval consumers (F160).

## Open questions

- **WebP support edge case:** `sharp` decodes nearly all input formats
  but a malformed PNG could throw. Behaviour: log + leave
  vision_derivative_path NULL + fall through to original. If original
  is also too big, Vision will 413 — same as today, no regression.
- **Concurrency limit on derivative generation.** sharp is CPU-bound;
  N concurrent encodes saturate the Fly shared-cpu-1x. We're already
  rate-limited to pLimit(4) on Vision calls; derivative-generation
  inherits that limit since it's inside the same loop. No new
  semaphore needed.

## Verification plan

`apps/server/scripts/verify-f165-1-vision-derivatives.ts`:

1. **Under-threshold path** — synthesize a 500 KB JPEG, call
   `ensureDerivative`, assert `isDerivative === false`,
   `vision_derivative_path` stays NULL, no `.webp` written.
2. **Over-threshold path** — synthesize a 7 MB JPEG (real or via
   sharp), call `ensureDerivative`, assert `isDerivative === true`,
   bytes returned are valid WebP (sniff magic), `< 5 MB`,
   long-edge `≤ 1568`, `vision_derivative_path` set in DB,
   file exists at that path.
3. **Idempotency** — call `ensureDerivative` a second time, assert
   no re-encode (compare mtime) and same bytes returned.
4. **Strict fallback** — unit-test `shouldFallback`:
   - `FetchTimeout` → true
   - `AnthropicApiError(status=503)` → true
   - `AnthropicApiError(status=413)` → false
   - `AnthropicApiError(status=400)` → false
   - `AnthropicApiError(status=401)` → false
5. **End-to-end** — submit a vision-rerun job for a KB that contains
   one over-threshold image; assert job completes, the image's
   vision_description is non-null, vision_derivative_path is set.
