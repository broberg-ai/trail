# F201.20 — Start at login (Ambient survives a Mac restart)

**Status:** in progress · parent epic F201 (Trail Ambient Capture)

## Motivation

Trail Ambient is a *background* capture agent. On 2026-08-19 Christian found it
simply gone: "Vores ambient app kører ikke længere - booter den ikke ved Mac
genstart?"

He was right, and the answer is worse than a bug — the feature was never built.
The app has **never** had any autostart mechanism:

- `~/Library/LaunchAgents/` holds `dk.broberg.trail.admin.plist` and
  `dk.broberg.trail.engine.plist` (the dev servers) — nothing for Ambient.
- `System Events → login items` lists only Google Drive and FigmaAgent.

Every time the app has been "running", it was because a cc session had just
run `scripts/bundle.sh` and called `open`. The first Mac restart erased it, and
nobody noticed until six weeks of ambient capture had silently not happened.

That is the real cost: an agent whose whole value proposition is *always-on*
was, in practice, on only for as long as the terminal session that started it.

## Scope

**In:**

- Register the app as a login item with **`SMAppService.mainApp`**
  (`ServiceManagement`, macOS 13+; our `LSMinimumSystemVersion` is 14.0).
- A menubar **"Start at login"** toggle whose checkmark is read from the OS
  (`SMAppService.mainApp.status`), never from a local cached boolean.
- Persist the owner's *intent* in `UserDefaults` so we can distinguish
  "never asked" from "deliberately turned off".
- **Self-heal after a rebuild.** `scripts/bundle.sh` does `rm -rf` on the
  bundle and recreates it at the same path. If macOS invalidates the
  registration when the bundle is replaced, the next launch re-registers —
  but only when the stored intent is `on`.
- A `--loginitem <on|off|status>` CLI flag, matching the repo's existing
  headless-harness convention (`--selftest`, `--neuraltest`, …), so the
  registration can be driven and **verified across process boundaries**
  without a GUI click.

**Non-goals (explicitly out):**

- **Moving the app to `/Applications`.** It lives at
  `apps/ambient-capture/dist/Trail Ambient.app`. Relocating it risks
  detaching the microphone / Accessibility TCC grants, which have been
  painful in this project before (see the signing note in `bundle.sh`:
  `watcher_started_untrusted` after a re-grant, 2026-07-02). Autostart is
  not worth re-litigating TCC. Revisit only if the app is ever properly
  distributed.
- **A LaunchAgent plist.** Two competing autostart mechanisms would
  double-launch the app. `SMAppService` is the Apple-blessed path for a GUI
  menubar app and surfaces in System Settings → General → Login Items, where
  the owner can see and revoke it. One mechanism, verified.
- Auto-update / relaunch-on-crash. Separate concern.

## Architecture

One new file, `Sources/TrailAmbient/LoginItem.swift`:

```
LoginItem
  .isEnabled            → SMAppService.mainApp.status == .enabled   (OS truth)
  .wantsLaunchAtLogin   → UserDefaults intent (nil = never decided)
  .setEnabled(_:)       → register() / unregister(), stores the intent
  .syncAtLaunch()       → first run: opt in. Later runs: re-register if the
                          intent is `on` but the OS lost it (post-rebuild).
```

Wired in two places:

1. `AppDelegate.applicationDidFinishLaunching` → `LoginItem.syncAtLaunch()`.
2. `AppDelegate.render()` → a "Start at login" menu item with
   `state = .on/.off` read from `LoginItem.isEnabled`.

The toggle reads the OS on every render, so if the owner revokes the item in
System Settings the menubar tells the truth instead of lying from cache.

## Why default-on for the first run

The owner's stated expectation is that a background agent boots with the Mac.
So the first launch opts in, and macOS shows its standard "Trail Ambient added
a login item" notification — visible and revocable. Once the owner has made a
choice (either way), we never override it.

## Verification (per the repo's verify-before-claim rule)

A login item is a *persisted setting*, so the same read-back discipline as a
save-field applies: the app reporting "enabled" from its own memory proves
nothing.

1. `--loginitem on` in one process.
2. `--loginitem status` in a **separate, fresh process** → must print
   `enabled`. The status comes from the OS's Background Task Management
   store, so a cross-process read is real evidence macOS persisted it.
3. Negative control: `--loginitem off` → fresh process reports
   `notRegistered`, and a subsequent normal launch does not re-enable it.
4. Rebuild control: run `scripts/bundle.sh`, launch, confirm the status is
   `enabled` again (self-heal) without a manual click.

A true reboot test is the only 100% proof and belongs to the owner; the
cross-process + rebuild checks are what can be proven from here, and the
plan says so rather than implying more.

## Dependencies

None. `ServiceManagement` is a system framework; no new SPM package.

## Rollout

Ships with the next `scripts/bundle.sh` build. No server, no secret, no
network — nothing to ship dark.
