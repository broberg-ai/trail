# F163.1 — Image Gallery: bulk-actions (multi-select + flag/delete)

> Bygger på F163's grid-panel: tilføjer view-toggle (cards ↔ list), multi-select med checkboxes på begge views, og bulk-actions for "flag" (rate down via F164 Phase 5) + "delete" (HARD-delete: DROP row + purge storage-blob). Vender to non-goals fra F163's oprindelige plan — det sker bevidst nu fordi Sannes 248-billede-corpus har en vis mængde meningsløst støj (graphics, decorative-fragments, små UI-elementer fanget af PDF-extraction) som curator skal kunne fjerne på tværs af 5-30 billeder ad gangen, ikke et ad gangen via lightbox. Tier: alle tenants. Effort: Medium — ~½-1 dag opdelt i 4 phases. Status: Planned.

## Problem

F163 v1 (shipped som `35a4ff6`) gør curator i stand til at browse + søge sit image-corpus, og rate billeder via 👍/👎 fra completion-modal'en (F164 Phase 5). To workflow-huller er kommet ud:

1. **Visuel scanning er besværlig i grid-mode for "find dårlige billeder"-jobs.** Card-grid'et viser 6 billeder per række (180px columns), 2-line clamped caption, kun page-badge som metadata. Når Sanne skal scanne 248 billeder for at finde de 30-50 der er ren støj ("dark gray rectangle", "small decorative element", page-numbers fanget som images), er card-grid'et OK til "browse for inspiration" men dårligt til "kvalitetskontrol". List-view (én række per billede med thumbnail + fuld caption + dimensions + page) ville matche kvalitets-scanning bedre.

2. **Per-billede sletning kræver én lightbox-åbning + én klik per billede × 30+ billeder** = unforgiving workflow. Med multi-select + bulk-action kan curator tjekke 30 billeder ad gangen, klikke "Slet (30)", svare på bekræftelses-modal én gang, færdig.

Konkret: Christian har lige scrollet Sannes Zoneterapi-bog-output og fundet sample-images som "dark gray or charcoal colored rectangular element" (side 36) og "small dark square or rectangular shape" (side 28) — Vision-API'en er ærlig nok til at sige "intet meningsfuldt at beskrive", og curator vil hellere slette dem end have dem fylde i corpus'et. F164 Phase 5 thumbs-down kvalitets-rating er for blødt et signal når billedet er objektivt useløst.

Bredere: enhver Trail-ejer der populater en billed-tung KB vil møde samme støj. PDF-extractors fanger uvilkårligt små grafiske elementer (page-numbers, decorative dividers, blank rectangles brugt til layout). Indtil vi har en pre-filter der detekterer dem ved upload-tid (F163.2?), er manuel cleanup the-only-way, og det skal være effektivt.

## Secondary Pain Points

- **Storage-spild**: 50+ useløse images × ~500KB hver = 25MB+ permanent disk-occupation per tenant, multipliceret over fremtidens kunder. Hard-delete frigør disken; soft-delete gør det ikke.
- **Search-noise**: image-search FTS'er over `vision_description`. Et billede beskrevet som "dark rectangle" matcher unfortunately på enhver query der nævner "rectangle" — fortyndes search-kvaliteten. Hard-delete fjerner dem fra FTS-indexet via cascade.
- **Sample-grid-quality på completion-modal**: F164 Phase 5's tilfældige sample-grid trækker 6 random described-images per job. Hvis 20% af corpus'et er støj, er chance ~70% for at mindst ét sample-billede er ubrugeligt — fordrejer "did it actually work?"-signalet. Fjernelse af støj-billeder hæver sample-quality.
- **Cross-page selection er svært** med kun grid'et: hvis curator ser 30 dårlige billeder fordelt på 4 sider, skal selectionen overleve "Hent flere"-paginering. State-design er enkelt (Set<imageId> på panel-level) men list-view med fuld caption gør det lettere at se hvad man har valgt.

## Non-goals (v1)

- **Ingen pre-filter ved upload-tid**. Vision-API'en eller en heuristic der auto-discarder "decorative"-billeder før de lagres er en separat feature (F163.2 territory). v1 er manuel cleanup; auto-detect er v1.5.
- **Ingen "Restore" / undo** efter hard-delete. Curator får en bekræftelses-modal der eksplicit siger "Permanent — kan ikke fortrydes". For v2 kunne vi tilføje 30-dage-trash-bin, men det er kompleksitet vi ikke betaler for før det vises som behov.
- **Ingen bulk re-rating eller metadata-edit**. Multi-select scope er kun "flag (thumbs-down) + delete". Bulk-edit af description er separat feature.
- **Ingen drag-to-select / shift-click range-select**. Standard click-to-toggle på checkbox er nok for v1; tastatur + range-select er v1.5 hvis curator efterspørger det.
- **Ingen export / download**. "Slet alle dårlige" + "behold alle gode" er v1 scope; "download alle gode som zip" er ikke.

## Solution

### Schema (ingen ny migration)

Hard-delete bruger eksisterende SQL-cascades:

```sql
DELETE FROM document_images WHERE id IN (?, ?, ...);
```

Cascades automatisk:
- `vision_quality_ratings` rows (FK → image_id ON DELETE CASCADE) — F164 Phase 5 ratings forsvinder med billedet
- `document_images_fts` rows (via DELETE-trigger fra migration 0025)

Storage-blob purge kører i samme handler — efter SQL-DELETE, før response. Best-effort: hvis storage.delete fejler, log warning men fortsæt (DB-state er den autoritative — orphan blobs kan GC'es senere).

### Backend — ny endpoint

`POST /api/v1/documents/:docId/images/:filename/delete` (single)

Eller bedre — bulk:

`POST /api/v1/knowledge-bases/:kbId/images/bulk-delete` body `{ imageIds: string[] }`

Vi vælger bulk-endpoint v1 fordi UI'en altid sender mindst én og typisk mange. Single-endpoint kan tilføjes hvis programmatisk-single-image-delete bliver et reelt behov.

```typescript
// apps/server/src/routes/images.ts
imageRoutes.post('/knowledge-bases/:kbId/images/bulk-delete', async (c) => {
  // 1. Resolve kbId, validate tenant scope
  // 2. SELECT id, storage_path FROM document_images WHERE id IN (?...) AND kb_id = ? AND tenant_id = ?
  // 3. DELETE FROM document_images WHERE id IN (?...)
  //    → cascades to vqr + fts via existing triggers
  // 4. For each storage_path: storage.delete(path) — best-effort, log on fail
  // 5. Return { deleted: number, storageWarnings: string[] }
});
```

**Tenant-scope guard** er kritisk: cross-tenant probe-attack ("guess image-id, delete") skal returnere 0 deleted, ikke fejle stille. JOIN på documents + tenants_id i SELECT, fail-closed hvis ANY image-id mangler scope.

**Audience-filter**: hvor F164 Phase 5 thumbs-down endpoint accepterer fra curator-audience, skal bulk-delete også. Bearer-keys (tool-audience) kan IKKE delete — det er en operator-only handling. Reject 403 hvis `c.get('authType') === 'bearer'`.

### Bulk-flag endpoint — også ny

`POST /api/v1/knowledge-bases/:kbId/images/bulk-rate` body `{ imageIds: string[], rating: 'down' | 'up' | null }`

Mapper til F164 Phase 5's rating-tabel via UPSERT-loop (ON CONFLICT(user_id, image_id)). Returnerer `{ rated: number }`.

Udspring fra Christian's "flag/delete" — flag = thumbs-down. Brugeren har bekræftet at separat `marked_for_review`-status IKKE er nødvendig; F164 Phase 5 thumbs-down er nok.

### Frontend — `images.tsx` udvidelse

#### View-toggle

```
┌──────────────────────────────────────────────────┐
│ [Search...] [Filter: source ▾]  [☷ Cards | ≡ List] │
└──────────────────────────────────────────────────┘
```

To icon-buttons øverst i toolbar. State persists per-tenant i localStorage (`trail.images.view`). Default = `cards`.

#### Multi-select på cards

Hver card får checkbox-overlay i top-left når selection-mode er aktivt (eller altid synligt med low-opacity hover-state). Klik på checkbox → toggle. Klik på resten af card → åben Lightbox som før.

```
┌────────────────────┐
│ [☐] (image)   p.4 │  ← checkbox top-left, page-badge top-right
│                    │
│   description...   │
└────────────────────┘
```

#### Multi-select på list

```
┌─┬────────┬─────────────────────┬────────┬────────┐
│☐│  thumb │ description         │ source │ p.4    │
├─┼────────┼─────────────────────┼────────┼────────┤
│☐│  thumb │ description         │ source │ p.7    │
└─┴────────┴─────────────────────┴────────┴────────┘
```

Tabel-layout, en række per billede. Thumbnail 80×80 cover. Caption full (ikke clamped). Source name, page, dimensions. Click-row → Lightbox (samme handler).

#### Selection-bar

Vises sticky øverst når selection > 0:

```
┌──────────────────────────────────────────────────┐
│ 12 valgt    [Vælg alle på siden] [Ryd]          │
│                                                   │
│             [👎 Flag (12)]  [🗑 Slet (12)]        │
└──────────────────────────────────────────────────┘
```

"Vælg alle på siden" kun aktiv hvis ikke alle currently-loaded hits er selected. Selection persisterer på tværs af `loadMore()` (Set lever i panel-state).

#### Bekræftelses-modal for delete

```
┌──────────────────────────────────────────┐
│ Slet 12 billeder?                         │
│                                            │
│ Dette fjerner billederne PERMANENT — kan ikke │
│ fortrydes. Tilhørende ratings og description- │
│ index slettes også.                            │
│                                                │
│ Storage-bytes (~6 MB) frigøres.                │
│                                                │
│         [Annullér]  [Slet permanent]          │
└──────────────────────────────────────────┘
```

`[Slet permanent]` knappen er rød (`color-danger`), ikke accent-farve. "Permanent" + "kan ikke fortrydes" er understreget for klarhed. Storage-frigørelse vises som transparency-touch.

Ingen confirmation modal for bulk-flag — thumbs-down er reversible (klik igen for at un-rate), så friction der ville bremse legit-batch-rating.

## Architecture sketch

```
images.tsx
   │ checkbox toggle → setSelected(Set<imageId>)
   ▼
Selection-bar visible when selected.size > 0
   ├─ Bulk-flag click → confirm? no → POST /bulk-rate
   │                                   → loop UPSERT in vision_quality_ratings
   │                                   → toast "12 markeret"
   │                                   → setSelected(empty)
   │
   └─ Bulk-delete click → confirm modal "12 billeder?"
                          → confirm → POST /bulk-delete
                                      → SELECT scoped rows
                                      → DELETE → cascades VQR + FTS
                                      → storage.delete(blob) per row, best-effort
                                      → return { deleted, storageWarnings }
                                      → toast "12 slettet, 6 MB frigjort"
                                      → refetch first page (state reset)
```

## Phases & verify scripts

### Phase 1 — backend bulk-delete + bulk-rate (1-2h)
- `apps/server/src/routes/images.ts` adds two endpoints. Tenant-scope JOIN, audience-guard (no Bearer for delete), best-effort storage.delete.
- Verify: `verify-f163-1-bulk.ts` — seeds 5 throwaway image-rows + storage-blobs, calls bulk-delete with 3 ids, asserts: 3 rows gone from DB, 3 blobs gone from disk, FTS row count -3, vqr cascade fires, cross-tenant probe returns 0 affected. Bulk-rate path: seeds 3 rows, calls bulk-rate(down), asserts 3 vqr rows present.

### Phase 2 — frontend selection-state + view-toggle (1-2h)
- `images.tsx` adds `selected: Set<string>`, view: `'cards' | 'list'`. Persisted view via localStorage.
- New `<ImageList />` component for list-view (table-row layout + checkbox + click-row → Lightbox).
- Update `<ImageTile />` for cards: add checkbox overlay, propagation-stop when checkbox clicked.
- Selection-bar component (sticky, visible when selected.size > 0). "Vælg alle på siden" / "Ryd" buttons.

### Phase 3 — bulk action wiring + confirm modal (½-1h)
- "👎 Flag (N)" button → POST bulk-rate, toast on success, clear selection.
- "🗑 Slet (N)" button → confirm modal → POST bulk-delete, toast w/ "deleted + storage freed", refetch first page.
- Modal styled red-accent (danger) per design system.

### Phase 4 — i18n + polish (½h)
- Danske + engelske keys for alle nye strenge.
- Loading states på bulk-buttons (`…` while in-flight).
- Empty-state copy update if all images deleted ("alle billeder er nu fjernet — upload nye kilder").
- Visual: list-view alternating-row-hover, checkbox accent-color matching design system.

Total: ~½-1 dag. 4 commits eller én bundlet commit afhængigt af review-præference.

## Open questions (resolved before plan-doc landed)

- ✅ **Hard vs soft-delete**: Christian's beslutning — **HARD-delete**. "billeder der bare ikke giver nogen mening eksempelvis s.36" implicerer permanent fjernelse. Ingen archived-flag på document_images.
- ✅ **Flag-semantik**: bruger eksisterende F164 Phase 5 thumbs-down. Ingen ny `marked_for_review`-status.
- ✅ **Confirmation modal**: ja for delete (irreversibel), nej for flag (reversibel via re-toggle).

## Resterende open questions (skal lukkes under impl)

- **Performance på 100+ bulk-delete**: én SQL-statement (`DELETE FROM ... WHERE id IN (?, ?, ...)`) er fint i SQLite til ~999 ids per query. Hvis curator nogensinde vælger >999, splittes i batches. Ikke et problem v1; flag for v2.
- **Storage-delete error-handling**: hvis storage.delete fejler på 1-2 blobs ud af 12, hvad gør vi? v1: log + return `storageWarnings` med blob-paths så curator kan se det. v2 kunne tilføje en automatisk retry eller en GC-job der scanner for orphan-blobs.
- **Audit-trail af deletions**: skal vi logge hvem-slettede-hvad-hvornår? Nuværende DELETE er anonym efter eksekvering. v2 kunne tilføje `image_deletion_log` table; v1 ignorerer det indtil der er en compliance-grund.
