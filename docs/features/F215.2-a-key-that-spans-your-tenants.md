# F215.2 — You cannot create a key that spans your tenants

**Status:** in progress. Found while the owner tried to use F215.1, an hour after it shipped.

## What happened

The tenant picker shipped in F215.1. The owner installed it, saw no picker, and
asked the reasonable question:

> "Skal jeg hente en ny token i app.trailmem.com?"

The answer was **no** — and that is the bug. A newly minted key would have been
locked to one tenant and shown him no picker either.

## Measured

Two separate problems wearing one symptom.

**1. The key in his Clipper is dead.** Read out of Chrome's own extension
storage rather than asking him to read a masked password field, and tested
against prod:

```
trail_95d866…   /api/control/my-tenants    401
                /api/v1/me/tenants         401
                /api/v1/knowledge-bases    401
```

All three. Not a scope problem — the key is simply invalid, most likely the one
rotated in F207 when the leaked web-clipper key was replaced.

**2. No key that would work can be created.** His working key (from
`.env.local-ingest`) answers 200 on all three and lists three tenants — it is
`scope='all'`. But `apps/admin-server/src/keys.ts:113` writes:

```ts
scope: 'full',
```

unconditionally. There is no parameter, no form field, no surface anywhere that
produces an `all` key. So F215.1's picker is correct and **unreachable**: it
renders only when the caller can see more than one tenant, and the product
cannot mint such a caller.

## The distinction this rests on

`scope='all'` is a **selector, not a grant**. It lets a key choose among the
tenants its user is *already a member of* — exactly the set the proxy verifies
on every request (F191.6). It confers no access:

- a slug the user is not a member of is refused, `all` scope or not;
- revoke the membership and the key narrows immediately, without touching the key.

So offering the choice at creation time widens nothing. What it removes is the
situation where the only key that can span tenants is one that happens to exist
from an earlier era and cannot be reproduced.

## Scope

### In

1. `POST /api/control/api-keys` accepts an optional `scope`, validated against
   `'full' | 'all'`, **defaulting to `'full'`**.
2. The Admin SPA's key form offers the choice in plain language — *this customer
   only* vs *all my customers* — defaulting to the narrow one.

### Out

- **Widening any existing key.** This changes creation, not stored rows.
- **A per-tenant allow-list on a key.** F205.1 owns restricted partner keys; a
  third scope model here would collide with it.
- **Changing where access is decided.** The membership join stays the single
  gate. A second place that decides access is how the two drift.

## Why the default must stay narrow

An omitted field must produce today's key. The alternative — defaulting to `all`
because it is more convenient — silently widens every caller that was written
before this change, including scripts nobody is going to re-read. A wider key
than the author believed they asked for is the failure worth engineering
against.

And an unrecognised scope is a **400**, never a coerce-to-default: a caller who
asks for `all` and receives a `full` key without being told has a key that will
fail later, somewhere else, looking like an access problem. That is the exact
shape of F210.5 and F214.1, twice already this week.

## Rollout

1. Route first, with its own proof — including the negative control that the
   same user's two keys differ only by scope.
2. Form second.
3. Then the owner mints a Clipper-specific key, and revokes both the leaked
   `trail_a3361a…` (pasted into a chat transcript today) and the dead
   `trail_95d866…`.

## Related, not folded in

- **F215.3** — remove the duplicate `/api/v1/me/tenants` this session created
  when `/api/control/my-tenants` already existed (F191.6). Two endpoints
  answering one question will drift.
- The Clipper's token field is masked with no way to reveal it, so the owner
  could not tell which key was installed. Its error message also said "check the
  token" while listing knowledge bases, mixing "the key is dead" with "this
  customer has no Trails".
