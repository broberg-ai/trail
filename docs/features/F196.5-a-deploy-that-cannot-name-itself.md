# F196.5 — A hand-rolled `flyctl deploy` loses the sha, and nothing complains

**Status:** backlog · **Parent:** [F196](F196-deploy-self-report-upmetrics.md) · **Found:** 2026-08-29, the hard way

## What happened

I deployed the engine at 09:15 with:

```
flyctl deploy --config apps/server/fly.toml --app trail-engine-001 --yes
```

The sanctioned path is `pnpm ship:engine`, which is the same command **plus**
`--build-arg GIT_SHA=$(git rev-parse --short HEAD)`. Mine had no build-arg, so
the Dockerfile's `ARG GIT_SHA=unknown` default won, and the app dutifully
self-reported:

```
{"site":"trail-engine-001","sha":"unknown","deployedAt":"2026-08-29T09:15:08Z"}
```

upmetrics accepted it. Nothing warned, nothing failed, and the release register
now held a row that says *a deploy happened* and cannot say *which code*.

**The cost was immediate and concrete.** Forty minutes later I needed to prove
that an F212.4 fix was live on production. I could not: the queue was empty, so
old and new code answered identically, and the one instrument that exists to
settle "which code is running" said `unknown`. I had to report the deploy as
**not runtime-verified** — for a fix that was, in fact, live. Re-shipping through
`pnpm ship:engine` produced `sha: 45e8ca7` and settled it in one request.

## Why it belongs in F196 rather than in a habit

F196.1 and F196.2 are correctly built. The helper reads `GIT_SHA`, the Dockerfile
declares the ARG, the ship scripts pass it. Every piece works. What is missing is
that **the one path where it silently does not work looks exactly like the one
where it does** — same command name, same green output, same successful report.

That is this week's shape once more: a success-shaped answer that withholds the
field it exists to carry. `sha: "unknown"` is the deploy register's version of
the lint drain's `rejected: 0` (see [F212.4](F212.4-a-dry-run-that-cannot-be-wrong.md)),
and of a form that says "Saved" without asking the database.

## Options (not yet decided)

1. **Warn at boot** when `GIT_SHA` is missing or `"unknown"` — cheap, but a log
   line nobody reads is weak medicine.
2. **Refuse to report** without a sha — rejected on sight: it trades a
   traceable-but-vague row for no row at all, which is strictly worse. A deploy
   that happened must always be recorded.
3. **Make the wrong path impossible** — a `predeploy` guard, or documenting the
   ship scripts as the only path. The strongest fix, and the one that does not
   depend on anyone reading anything.

The ACs cover (1) because it is the part that belongs in the code we own; (3) is
a repo-convention question worth Christian's call, since it constrains how
anyone deploys.

## Non-goals

- Changing the upmetrics contract (locked, #4223). `sha` stays a plain string;
  this card is about what we put in it.
- Adding a version endpoint to the engine. That is a different answer to a
  related question and deserves its own card if wanted — note that during this
  incident `GET /api/v1/version` and `/health` both 404'd, so the release
  register was genuinely the only outside view of what was running.

## Note

Whoever builds this: the guard has to land in **both** report paths —
`packages/shared/src/upmetrics.ts` (Bun apps) and `apps/*/report-deploy.sh`
(nginx apps). Fixing one and not the other reproduces the exact split that let
this survive, and the nginx copies are byte-identical today, so they drift as a
set or not at all.
