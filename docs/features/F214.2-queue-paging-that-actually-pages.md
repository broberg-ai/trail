# F214.2 — `?cursor` is accepted and never used, so a caller pages the same rows forever

**Card:** trail-F214.2 · **Parent:** F214 (a rejected form must say which field) · 2 SP

## Motivation

`ListQueueQuerySchema` declares `cursor: z.string().optional()`. `listCandidates`
never reads it. The query is `.orderBy(desc(createdAt)).limit(query.limit)` and
nothing else.

So a caller who writes a paging loop from the schema — which is the honest way to
discover an API — gets HTTP 200, a full-looking page, and **the same rows every
time**. Nothing errors. Nothing warns. The loop terminates only when the author
decides it has "enough".

Measured on prod 2026-08-29 (broberg-ai):

```
count                    7403      ← the real total
limit=200                 200 rows
limit=201                 400 "must be ≤ 200"
offset=5                  same first row      (offset was never the API)
cursor=<anything>         accepted, ignored, page 1 again
response keys            ['count','items']    — no nextCursor
```

**200 of 7,403 rows are reachable.** The remaining 7,203 cannot be fetched by any
combination of documented parameters.

This is worse than a missing feature. A missing `cursor` would produce a 400 and
the author would go and read something. A *declared* `cursor` that does nothing
produces a green build over a wrong answer — the failure form this repo has met
five times in a week (F212.4's `rejected: 0`, F210.5's silent `addBearer` no-op,
F214.1's ZodError-as-500, `@broberg/secret-scan`'s `findings: []`, and buddy's
"15 lines starting with `TRAIL_`" read as "the three specific ones").

The peer that would have written that loop said so plainly (#23846): *"Intet ville
have fejlet."*

## The measurement that decides the design

`createdAt` is stored as second-resolution `YYYY-MM-DD HH:MM:SS`, and it collides:

```
200 rows sampled → 190 distinct createdAt → 10 collisions
```

A cursor keyed on `createdAt` alone would therefore **skip or duplicate rows at
every page boundary where two candidates share a second** — silently, and only
under load, which is when it matters. Batch writes (an ingest run, a lint sweep)
are exactly the case that produces same-second rows, so the collisions are not
uniformly scattered: they cluster.

The cursor is a **composite of `(createdAt, id)`**, and the sort gains `id` as a
tiebreak, because a keyset cursor is only correct over a *total* order.

The format is uniform (all 200 rows SQL-space, none ISO-Z), so lexicographic
string comparison is a valid time comparison here. This is asserted in the verify
script rather than assumed — if a second format ever lands in the column, the
assertion goes red instead of the paging going quietly wrong.

## Scope

**In:**
- `cursor` is honoured: keyset paging on `(createdAt DESC, id DESC)`.
- Response gains **`nextCursor`** — a string when more rows exist, `null` when the
  page is the last one. This is also what makes AC2 exact: truncated and complete
  pages become distinguishable by a field, not by counting.
- An unparseable `cursor` returns **400 naming the field**, never a silent restart
  from page 1. (A silently-ignored bad cursor is the original bug wearing a
  different hat.)
- `count` semantics unchanged.

**Explicit non-goals:**
- No `offset`. The card's original text said `?offset` was silently ignored; that
  was imprecise — offset was never the API. Implementing it now would add a second
  paging contract that skews under concurrent inserts, next to a correct one.
- Not raising the 200 cap. The cap is fine once paging works.
- No change to ordering *semantics* (newest first stays newest first); `id` is a
  tiebreak within an existing sort, not a new sort.

## Architecture

```
cursor  =  base64url( `${createdAt}|${id}` )     — opaque to the caller
keyset  =  createdAt < C.createdAt
           OR (createdAt = C.createdAt AND id < C.id)
order   =  createdAt DESC, id DESC
```

`listCandidates` fetches `limit + 1` rows. If it gets more than `limit`, a further
page exists: it returns the first `limit` and a `nextCursor` built from the last of
them. This makes "is there more?" a **fact read off the database**, not an
inference from `items.length === limit` — which is wrong exactly when the total is
an exact multiple of the page size.

Why keyset and not offset: rows are inserted continuously (ingest, lint, chat). An
offset page re-reads a shifting window and both skips and repeats rows under
concurrent insert. A keyset cursor is stable against inserts *newer* than the
cursor, which is the direction this table grows.

## Dependencies

None. `packages/shared` (schema), `packages/core` (query), `apps/server` (route).
No migration — `id` and `createdAt` are both already indexed as part of the table.

## Rollout

Additive and backward-compatible: a caller that sends no `cursor` gets exactly the
page it got yesterday, plus one new field it can ignore. No consumer is cut over.

The Admin SPA's queue panel does not page today; it is unaffected.

## Verification

`apps/server/scripts/verify-f214-2.ts`, run against a real migrated DB, must prove:

1. Two consecutive pages are **disjoint** (strict set comparison of ids), and their
   union equals the first `2×limit` of a single unpaged read in the same order.
2. Paging the *whole* filter reaches `count` rows exactly — no row seen twice, none
   missing. This is the assertion the old code could never pass.
3. **Same-second rows are not skipped**: seed rows sharing one `createdAt` that
   straddle a page boundary, and assert every one is returned exactly once. This is
   the collision case measured above and the reason `id` is in the cursor.
4. A truncated page has `nextCursor !== null`; the final page has `nextCursor === null`.
5. `count` is unchanged by `limit` and by `cursor`.
6. A malformed `cursor` → 400 naming `cursor` (negative control: it must not
   silently return page 1).
7. **Mutations**, each reddening a different assertion:
   - drop `cursor` from the query → the disjoint assertion goes red;
   - drop `id` from the cursor/tiebreak → the same-second assertion goes red;
   - always emit `nextCursor` → the last-page assertion goes red.
