# F199.10 — Ingest cloud fallback → Mistral EU, and why NOT size-escalated to large

## Motivation

Ingest is Trail's largest customer-data surface — the compile prompt embeds the
**entire source document** (F199's audit flagged this as the gap left after
F199.1–.9: chat/vision/discrete-services were on Mistral, but the ingest cloud
fallback chain still routed through Gemini/GLM/Qwen — US and Chinese models —
for the highest-risk data path). Christian's directive: *"Mistral er vores nye
go-to for alt data der kan have personligt indhold."*

Christian also proposed a natural-sounding refinement: escalate small→large
sources to `mistral-large-latest` so a bigger/harder document doesn't lose
Neurons on a cheaper model ("vi skulle jo nødigt miste gode neuroner"). This
plan-doc documents why that escalation was tested **and rejected** — the data
says the opposite of the intuitive assumption.

## Empirical testing (4 tool-loop runs against the REAL ingest pipeline)

Method: seeded a throwaway temp DB per run, called the REAL `buildCompilePrompt()`
(tag/entity/schema/language-aware, identical to production) and the REAL
`createCandidateQueueAPI()`, drove the exact same 4-tool loop shape as
`OpenRouterBackend`/`MistralBackend`, and measured **fact recall** — a hard,
grep-based count of known facts from the source that survived into the
compiled Neurons (not a subjective read).

| Test | Source | mistral-small-latest | mistral-large-latest |
|---|---|---|---|
| 10a | 1-page synthetic (30 facts) | 25/30 (83%), $0.015 | 24/30 (80%), $0.090 |
| 10b | 3.2-page synthetic (42 facts) | 34/42 (81%), $0.019 | 22/42 (52%), $0.145 |
| 10c | **Real 15-page excerpt of a customer's clinical PDF (with embedded images)** — Sanne Andersen's "Zoneterapibogen_2026.pdf" (124-page book; tested pages 30-44, 25 facts), Christian-approved with a $5 test budget | 21/25 (84%), $0.044 | 1/25 (4%), $0.162 |

`mistral-large-latest` did not win a single test. On the real customer source
(10c) it nearly failed the task outright (1 Neuron, capturing 1 of 25 facts,
at the highest cost of any run).

**Reference point (not a candidate — non-EU, informational only):**
`deepseek/deepseek-v4-pro` via OpenRouter scored 23/25 (92%) on the same 10c
source at $0.149. This confirms the ~80-84% ceiling isn't a limitation of the
task or harness — a stronger/faster model can do meaningfully better. The
finding is specific to `mistral-large-latest` in this tool-loop, not "bigger
models always do worse."

## Mechanism

Both backends share the same `maxTurns` budget. `mistral-large-latest` is
slower per-turn (more reasoning per call), so **within the same turn budget it
gets through less of the document** before the loop ends — it isn't "worse
reasoning," it's "covers less ground before running out of turns." Small's
speed lets it iterate through more of a long document in the same budget,
which matters more than per-call depth for this specific task shape (compile
= walk the WHOLE document, write many small Neurons).

## Decision

- **Ship `mistral-small-latest` as the ingest default** — cheap, EU, and it
  matched or beat `mistral-large-latest` on recall in every test, including
  the real customer source.
- **`mistral-large-latest` stays available** in the model registry and the
  fallback chain (as a same-provider resilience step, not a quality upgrade)
  for manual per-KB override, but is **NOT auto-selected by document size**.
  The evidence argues directly against that — it would make ingest worse and
  more expensive, not safer.
- **No new size-classification logic was built.** Building an auto-escalation
  feature the data disproves would be complexity theater.

## What shipped

- `apps/server/src/services/ingest/mistral-backend.ts` — new `MistralBackend`
  (mirrors `OpenRouterBackend`'s tool-loop, pins `override:{provider:'mistral'}`
  — true EU residency via api.mistral.ai, not an OpenRouter US-transit).
- `packages/shared/src/ingest-models.ts` — `IngestBackendId` gains `'mistral'`;
  registry entries for `mistral-small-latest` (default, `quality:'great'`) and
  `mistral-large-latest` (`quality:'best'`, available override) with honest
  descriptions referencing this finding.
- `apps/admin/src/api.ts` — mirrored `IngestBackendId` union update (admin's
  own duplicate type, same as the F149/F152 pattern).
- `apps/server/src/services/ingest/runner.ts` — `MistralBackend` wired into
  the `BACKENDS` registry.
- `apps/server/src/services/ingest/chain.ts`:
  - New `DEFAULT_CHAIN_MISTRAL` = `[mistral-small, mistral-large, gemini-2.5-flash]`
    (gemini kept only as a last-resort if Mistral's API is fully unreachable).
  - `DEFAULT_CHAIN_CLAUDE_CLI`'s fallback tail (fires only when local Max/
    claude-cli fails) now routes through Mistral before Gemini, closing the
    same GDPR gap for the $0 local-ingest primary path.
  - `resolveIngestChain` gains an explicit `INGEST_BACKEND=mistral` branch.
  - Existing precedence (KB full-chain override → KB single-step → env
    override → hardcoded default) is **completely unchanged** — verified with
    a runtime probe that a KB-level override still wins over the new
    Mistral-flavoured default.
- `docs/features/F199-ai-provider-exit-deanthropic.md` — story list updated.

## Non-Goals

- NOT building document-size classification/chunking (that's F142's job,
  already scoped separately — a 124-page book is out of F199.10's scope
  entirely; this story is about *model choice*, not document splitting).
- NOT changing local-ingest (F191, $0 Max) — Christian confirmed it's correct
  as-is; this story only touches the *cloud* ingest fallback chain.
- NOT removing `mistral-large-latest` from the registry — it remains a valid
  manual choice for a curator who wants to experiment, just not automatic.

  → `DEFAULT_CHAIN_MISTRAL` exactly; no env → `claude-cli` primary unchanged
  (Mistral only in its fallback tail); a KB-level override still wins over the
  env-mistral default.
- Full-repo typecheck (`packages/shared`, `apps/server`, `apps/admin`) clean.
- Deployed to `trail-engine-001` (commit hash in the shipping commit).

"Zoneterapibogen_2026.pdf") was fetched read-only via the cloud API into an
