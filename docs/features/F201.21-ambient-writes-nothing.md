# F201.21 — Ambient captures, and saves nowhere

**Card:** trail-F201.21 · **Parent:** F201 (Ambient Capture) · 3 SP · critical

> Owner-reported, 1 September 2026: *"Trail Ambient virker ikke længere - den gemmer
> ikke automatisk aktivitet i den designated trail."*

He is right. It has been true since **3 July** — two months — and nothing said so.

## What was measured, before anything was changed

### The silence is real, and dated

| Query (tenant broberg-ai) | Result |
|---|---|
| `?connector=trail-ambient-capture` | **281** total — 151 approved, 130 rejected, **0 pending** |
| newest candidate | **2026-07-03 19:27:23** |
| KB `cb-m1` documents | 126 — newest real entry also **2026-07-03** |

Both write paths are silent. So this is **not** F201.13's source-first change
routing writes somewhere unexpected — there is nothing in either place.

### The server half is healthy — proven, not assumed

The agent's own token was read from the login Keychain (account
`trail-api-token`; the value was never printed) and used to drive the real
endpoints:

```
GET  engine-001/api/v1/knowledge-bases  → 403   correct — an 'ambient' key is allow-listed
POST engine-001/api/v1/queue/candidates → 201   cnd_8e116137-90f, compiled into a Neuron
```

Token alive, KB id right, scope sufficient, engine accepting. **The break is on
the Mac.**

> The first probe returned `400 metadata: Expected string, received object` — my
> own malformed body, not a defect. `metadata` is a JSON **string** here, which is
> what the Swift client sends. Recorded so the 400 is not later mistaken for a
> finding.

### The running agent corresponds to no build in the repo

```
pid 37623   started 21 Aug   apps/ambient-capture/dist/Trail Ambient.app/…/TrailAmbient
ls apps/ambient-capture/dist/   →  No such file or directory
```

The executable has been **unlinked while the process kept running** — macOS
allows this. So the agent has been capturing for eleven days as code that exists
nowhere on disk. *Any* conclusion drawn from its behaviour is a conclusion about
unknown source, which is why the first step below is a rebuild rather than more
diagnosis.

A **second** process (63906) started today at 21:06, so there may be two
instances contending for the capture devices.

### Capture starts, and is interrupted — every 20-30 minutes

```
recordingDidStopWithError:movieURL:
updateStateWithActive:error:  update state with isActive 0 error 1
connection interrupted, stopping audio capture
```

ScreenCaptureKit sessions begin (a TCC request plus `getShareableContent` every
~20s) and then die with error 1. A capture that never completes yields no
segment, so the gate never runs and there is nothing to POST.

**[Likely], not proven** — and the gap matters: this process only started on
21 August, while the silence begins 3 July. Today's interruptions cannot be the
thing that stopped it two months ago. Either there are two faults, or one cause
with an older origin. Do not close this card on the interruption alone.

## Why two months passed unnoticed

The menubar shows the agent as running, because it *is* running. The OS shows
capture activity, because capture is being attempted. Nothing in the system ever
compares **"am I capturing"** with **"did anything reach Trail"**.

This repo's recurring shape, again: *one signal, two facts.* "Running" and
"working" were reported by the same green icon, and only the owner opening Trail
and finding it empty could tell them apart.

That is why AC5 is not a nicety. A fix without it buys silence until the next
regression.

## Approach

1. **Rebuild from source and run a known binary.** Turns "unknown code" into a
   fact before any further diagnosis. Check for a second instance first.
2. **Instrument the write path**, so a failure names itself: gate verdict,
   POST status, and the reason a capture produced nothing.
3. **Fix the named cause.** Not "it works after a rebuild" — that is a restart,
   not a diagnosis, and it will come back.
4. **Add the write-health signal** (AC5) and the probe script (AC6).

## Non-goals

- Not re-opening gate thresholds. If the gate is rejecting everything, that is a
  measurement to take, not a number to lower until rows appear.
- Not redesigning capture. The audio/screen stack is F201.5/F201.6's territory.
- Not touching the engine. It answered 201 on the first correctly-formed request.

## The one thing needing the owner

Restarting or killing the running agent is a live process on his Mac, and
`kill`/restart sits on the destructive list. It waits for his direct order.
