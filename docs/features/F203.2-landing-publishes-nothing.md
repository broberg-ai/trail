# F203.2 — Landing CODE cannot reach production, and the CMS deploy reverts it

**Status:** open · found 2026-08-23 while publishing the Chrome Web Store
privacy policy (F208.3)
**Parent:** F203 — Landing has a dead Fly deploy path
**Priority:** high

## Correction — what this story first claimed, and what measurement showed

The first draft of this plan claimed *"the two content stores have diverged and
the CMS wins"* and that two months of committed content had reached nobody.
**That was wrong, and it was written before the check that would have caught
it.** Recording it because the wrong version is the more tempting story: the
site's newest deploy is two months old, and it is easy to read staleness as
loss.

Measured afterwards:

```
git log --since=2026-06-24 -- apps/landing/content     → EMPTY
```

No landing content has changed since the last deploy. Nothing was lost, because
nothing was waiting. And every content document is live:

| | in repo | live on www.trailmem.com |
|---|---|---|
| pages | 2 | 2 × 200 |
| posts | 9 | 9 × 200 (`/trails/:category/:slug`) |

cms-core independently confirmed their half: the CMS holds `home` and
`the-1945-concept`, and `the-1945-concept` is live. Content is in sync.

## The real failure

`/pricing` returns 404, and it is not a content document — `pricing.json` has
never existed. The pricing page is generated by **`apps/landing/build.ts`**:

```
482ce77  feat(landing): pricing page + models section on homepage
         apps/landing/build.ts              +387
         apps/landing/content/global/global.json  +4
```

The repo's committed build output (`apps/landing/deploy/`) contains
`pricing/`. It was pushed live once, directly to `gh-pages` (`2b23625`). Then
`c9b9008 "Deploy from webhouse.app — 24.6.2026"` rebuilt `gh-pages` from the
CMS's own copy of the site — an older `build.ts` with no pricing page — and the
page disappeared.

So the divergence is **code, not content**:

- **Content** flows repo ⇄ CMS ⇄ live, and is consistent. The CLAUDE.md HARD
  RULE works.
- **Code** — templates, styling, `build.ts`, whole new generated pages — has no
  path to production at all. `.github/workflows/landing-deploy.yml` runs
  `flyctl deploy` against the Fly app `trail-landing`, which does not exist
  (F203). Every push has failed since May.
- When the CMS next deploys, it rebuilds from **its** copy of the code, so any
  landing code change made in this repo is silently reverted on the live site.

**Sharpened 2026-08-23 by cms-core**, and it is worse than "when the CMS next
deploys". The site is configured `deployProvider: github-pages`,
`deployAppName: broberg-ai/trail`, **`deployOnSave: true`** — so *every save in
the CMS republishes the whole site*. There is no manual deploy step anyone could
forget or postpone. Any file on `gh-pages` that does not originate in the CMS is
overwritten the next time an editor presses save on anything at all. `/pricing`
did not lose a race with a scheduled job; it was removed by someone editing an
unrelated page.

That also means the window between "push landing code to gh-pages by hand" and
"it is gone" is however long it takes for the next content edit to happen. Any
fix that relies on pushing built output directly to `gh-pages` is not a fix.

The repo's CLAUDE.md says *"Code edits to `apps/landing/` itself (templates,
blocks, styling, build scripts) stay in this repo and ship via PR."* They ship
via a PR into a branch that has no route to the live site. `/pricing` is that
sentence being false, in production, for two months.

## Open questions (Christian + cms-core)

1. **Where does landing CODE live — this repo, or the CMS's copy?** Two copies
   of `build.ts` exist and one of them wins every deploy. Whichever loses should
   stop being edited.
2. **How does a landing code change reach production?** Today: it cannot. If the
   CMS deploy is the only pipeline, it must build from the authoritative code.

## Scope

**In:** give landing code one route to production, prove it, and make a
reverted deploy impossible to miss.

**Non-goals:**

- The Pages-vs-Fly decision (F203.1 owns it).
- Rewriting the landing site or its build.
- Any change to how landing *content* is authored — that rule stands and is
  measured to work.

## Verification

A green workflow is not the bar; the failing workflow was green-adjacent noise
for three months. The bar is a **negative control**: change something in the
repo's landing code that is visible in the built HTML, ship it the sanctioned
way, then fetch the live URL and match that exact marker with strict equality.
Then re-fetch after a CMS deploy and confirm the marker survived — that is the
half `/pricing` failed.
