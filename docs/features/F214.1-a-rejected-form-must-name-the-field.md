# F214.1 — Turn a rejected body into a 400 that names the field

**Status:** built, verified locally, NOT yet deployed.
**Reported by:** the owner, 2026-08-28 ~01:38, in the product.

## What he saw

> "Jeg får 500 når jeg forsøger at gemme en opdatering af indstillinger for FD
> Aalborg tenant og trail Admin Chat - lidt træls da jeg har fyldt felterne op
> med tekst"

A save that fails is annoying. A save that fails and cannot say why, on a form
you have just filled with text, is the version that costs the work.

## Measured before anything was changed

```
2026-08-27T23:38:21Z  PATCH /api/v1/knowledge-bases/10096de6-…  500  7ms
```

And nothing else — in either app's log. KB `10096de6` is **"Admin Chat" in the
`fd-aalborg` tenant**; its stored description was 128 characters, so a short one
had saved fine before.

The 7 ms is itself a clue: too fast to be a database or a network problem. It
failed before it did any work.

## Root cause

Six engine routes validate like this:

```ts
const body = UpdateKBSchema.parse(await c.req.json());
```

Zod's `.parse()` **throws**. The throw landed in `app.ts`'s global handler,
which treated every throw as a server fault:

```ts
app.onError((err, c) => {
  captureException(err, …);
  return c.text('Internal Server Error', 500);
});
```

Three separate failures compounded into what the owner saw:

1. **A validation failure was reported as a server fault.** The client did
   nothing wrong that the server could not describe precisely — it simply
   never described it.
2. **The body was plain text.** The SPA's fetch wrapper reads `body.error` off
   JSON; `res.json()` threw, and it fell back to the status line. So even the
   little information there was could not reach the screen.
3. **Nothing was logged.** The request line said 500 and no line said why. That
   is why this needed a screenshot from the owner to find at all.

And upstream of all three: **the form accepted text the server was always going
to reject.** The description textarea had no `maxLength`; the schema capped it
at 500. Every other field on that panel was already bounded — name at 100, both
persona editors at 4000, lint cadence a dropdown. The description was the only
door to this failure, and it was standing open.

## The fix

### 1. `onError` distinguishes the two kinds of wrong

A `ZodError` becomes a **400** carrying `error: "<field>: <message>"` and a
machine-readable `issues[]`. Everything else stays a **500** — and now logs.

Handled centrally rather than at each call site on purpose: the bug is identical
at all six, and a per-route `try/catch` has to be remembered at the seventh.

The reverse direction is load-bearing and is asserted: a non-Zod throw must
still be a 500. Without that control this change could quietly reclassify every
real outage as "you sent a bad request" — and outages would stop reaching the
error board.

### 2. One source for the limits

`KB_NAME_MAX` / `KB_DESCRIPTION_MAX` / `KB_PERSONA_MAX` now live in
`packages/shared/src/schemas.ts`. The Zod schema validates against them and the
form's `maxLength` reads the same constants, so the two cannot drift. This is
the repo's own one-source rule applied to a number that had been written twice
and agreed once.

### 3. The form shows the limit

`maxLength` on the description textarea plus a live `n / 500` counter. The point
is not to prevent the 400 — it is that the limit is visible **while writing**,
not discovered by losing a save.

## What is deliberately NOT changed

- **The 500-character cap stays.** The bug was never that the limit exists; it
  was that nothing said so. Widening a stored-data limit is the owner's call,
  not a side effect of an error-handling fix.
- **Clearing the field stores `''` from one client shape and `NULL` from the
  other.** Both render empty. The first draft of the test demanded `NULL`, went
  red on `''`, and would have had me editing the handler to satisfy a test
  rather than a user. The assertion is on emptiness.

## Proof

`apps/server/scripts/verify-f214-1.ts` — 18 assertions through the real route
against a real migrated database. Reads every stored value back with **raw SQL**,
never through the layer that wrote it.

Two mutations, and the second one found a hole in the test rather than the code:

| Mutation | Result |
|---|---|
| **A** — ZodError branch disabled (i.e. the shipped bug) | 8 red, including the unreadable plain-text body. Every happy-path control stayed green, so the suite discriminates rather than merely failing. |
| **B** — the new log line deleted | **0 red.** The log line was half the fix and completely unproven. An assertion capturing `console.error` around a deliberate throw was added; the same mutation now goes red. |

Mutation B is the finding worth keeping: the part of a fix that exists to make a
future failure *visible* is the part a test is least likely to cover, because
nothing about the feature's behaviour changes when it is missing.

## Rollout

1. Deploy engine + admin (owner's order required).
2. Lens-verify the description field on prod: paste past the limit, assert the
   field holds exactly 500 and the counter reads `500 / 500`.
3. Re-save the Admin Chat settings that failed, and read the value back.
