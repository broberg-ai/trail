# F112.2 — User-note searchable internally (opt-in gated)

> Extends F112.1's share-toggle to also surface notes in `/search` results, not just chat + F160 retrieve. Same opt-in semantics: private notes never appear in search, shared notes appear with a 📝-prefixed snippet highlight. Tier: alle. Effort: Tiny — ½ time. Status: Done 2026-05-05.

## Problem

F112.1 wired user-notes into chat retrieveContext + F160 retrieve gated on `user_note_share=1`. But internal search still only hit `documents_fts` + `chunks_fts` — neither indexed `user_note`. Curator who shared a note about "Obi-wan Kenobi" couldn't find the parent Neuron when searching for that exact phrase, even with share enabled.

Christian flagged 2026-05-05: "output fra noten kommer med et datagrundlaget for chat og intern søgning samt som ekstern potentiel integration." All three consumers should honour the share-flag uniformly.

## Solution

New `searchUserNotes(query, kbId, tenantId, limit)` helper in `packages/db/src/search.ts`. Plain LIKE-scan over `documents.user_note` filtered by `user_note_share=1 AND archived=0`. Multi-word queries are AND'ed (every term must appear in the note). Hit's highlight is a manually-built snippet wrap of the first matching term so the UI renders consistently with FTS hits, prefixed with 📝 to visually distinguish "this hit comes from a curator note" from "this hit comes from Neuron body".

Search route merges note-hits into the documents-result, deduplicating by id (FTS hits keep their slot when both match — richer highlight wins).

## Why LIKE, not FTS5

`documents_fts` virtual table doesn't include `user_note` today; adding it would require:
- Migration 0035 dropping + recreating documents_fts with new column
- Trigger rewrites for INSERT/UPDATE/DELETE sync
- Backfill of existing rows

LIKE scan is O(n) per row but n is bounded by `WHERE user_note IS NOT NULL AND user_note_share=1` — usually <5% of documents. Notes are short (<4000 chars). At single-tenant scale with sub-second queries, FTS migration is premature. Revisit when a tenant has >10k shared notes (Sanne is far below).

## Privacy invariant

Same opt-in stance as F112.1:
- `user_note_share=0` (default): note exists on disk, visible only in wiki-reader's "Din tanke" section, NEVER in search/chat/retrieve.
- `user_note_share=1`: note flows into all three consumer surfaces.

Static probe (verify-f112-user-note.ts) checks chat.ts + retrieve.ts gate every `user_note` read on `userNoteShare`. Search route inherits this via the dedicated `searchUserNotes` helper which hard-codes `WHERE user_note_share = 1` in SQL.

## Non-goals

- **FTS5 ranking on note hits** — LIKE-search assigns synthetic rank 0.5 (slightly behind FTS hits). Order within note-hits is insertion-order from the SELECT.
- **Multi-language fold** (DA↔EN) — F148-style language fold isn't applied here. If demand surfaces (curator searches "tanke" wants to also match "thought"), revisit.
- **Snippet ranking** — first matching term gets the highlight; multi-term queries don't get composite highlights. Acceptable for short notes.

## Technical Design

### Helper function

`packages/db/src/search.ts:searchUserNotes` — returns `DocumentSearchHit[]` shaped identically to `searchDocuments` so route can union without per-hit shape mapping.

### Interface + adapter

`TrailDatabase.searchUserNotes` added to interface; `LibsqlTrailDatabase.searchUserNotes` delegates to the helper.

### Route integration

`apps/server/src/routes/search.ts` — `Promise.all` now fans out to 3 queries (docs FTS + chunks FTS + notes LIKE) and merges note-hits into the documents-result, dedup by id. Tag-filter + audience-filter still apply downstream so a `user_note` hit on an audience-hidden Neuron is suppressed correctly.

### UI

No changes — admin search panel already renders document-hits via `highlight` field. The 📝-prefix in the highlight string is the only visual indicator that a hit came from a note vs. body.

## Rollout

Single-phase deploy. No migration. Engine + admin restart picks up new route + helper.

## Success Criteria

1. Search for a unique phrase that exists ONLY in a shared user-note returns the parent Neuron.
2. Same phrase in a private (share=0) user-note returns NOTHING.
3. FTS hit + note hit on the same Neuron renders ONCE (FTS slot wins).
4. Multi-word query AND-semantics work (`"obi kenobi"` matches a note containing both terms).
5. Audience filter still applies — searching with `?audience=public` doesn't surface heuristic-tagged Neurons even if their note matches.

## Effort estimate

**Tiny** — ½ time.
