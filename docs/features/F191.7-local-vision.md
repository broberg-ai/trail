# F191.7 — Local vision (defer image description to the $0 cc session)

**Parent:** [F191 — Local Ingest Station](F191-local-ingest-station.md)
**Status:** building
**Owner:** trail cc session

## Motivation

F191 makes the **compile** step $0 (an interactive cc session does the
reasoning instead of the paid cloud LLM). But **vision** — turning an image
into a text description — still ran on the **paid cloud Haiku** during
extraction, regardless of `localCompile`. So images were the one leak in the
$0 promise (verified 2026-06-04). Two paths leak:

1. **Standalone image source** (drop a `.png`/`.jpg`): `image/pipeline.ts`
   calls `describeImageAsSource` INLINE during extraction → paid Haiku → the
   description becomes `documents.content`.
2. **Embedded images in PDF/DOCX/PPTX** (F164/F165): extraction stores the
   image rows in `document_images` (no LLM), then `uploads.ts` queues a
   `vision-rerun` background JOB that calls paid Haiku to fill
   `document_images.vision_description`. **This fires regardless of
   `awaitingLocalCompile`** (uploads.ts:1009 — the bug).

Claude (the cc session) is **multimodal** — it can see an image and describe it
for $0 on the Max plan. So both vision paths should be deferred to cc, exactly
like compile.

## Scope

**In:**
1. **Gate cloud vision on `awaitingLocalCompile`** (apps/server/src/routes/uploads.ts):
   - Standalone image + localCompile → pass a *deferred* `describeImageAsSource`
     that returns a `$0` placeholder marker (no LLM call), so the source parks
     with a small "awaiting local vision" body instead of a paid description.
   - Embedded images + localCompile → **skip** the `vision-rerun` job submission
     (gate the block on `!awaitingLocalCompile`). The image rows sit with
     `vision_description = NULL`, waiting for cc.
2. **REST endpoints the `/local-ingest` skill uses** (cc fetches bytes, views
   the image in-turn via the Read tool, writes the description back — all $0):
   - `GET /documents/:docId/raw` — raw **source** file bytes (for a standalone
     image; cc downloads → Reads → describes).
   - `GET /documents/:docId/images?pending=1` — list the doc's **embedded**
     images with `vision_description IS NULL` (`{id, filename, page}`).
   - `GET /documents/:docId/images/:filename` — embedded image bytes (EXISTS).
   - `POST /documents/:docId/images/:filename/local-vision` — write a
     cc-produced description: `UPDATE document_images SET vision_description=?,
     vision_model='claude-code', vision_at=now, vision_cost_cents=0`. ($0)
   - Standalone description is written via the existing
     `PUT /documents/:docId/content`.
3. **`/local-ingest` skill — image step**: before compiling a source,
   - if it's a standalone image (`fileType` ∈ png/jpg/jpeg/webp/gif/svg):
     `GET /raw` → save to /tmp → **Read the image file** (cc sees it) →
     describe → `PUT /content` with the description → then compile as normal.
   - for ANY source: `GET /images?pending=1`; for each, fetch bytes → Read →
     describe → `POST .../local-vision`. (PDF/DOCX/PPTX embedded images.)
   The vision is cc's own turn-reasoning — **$0, never `claude -p`, never an API key.**

**Non-goals:**
- Per-image free-run telemetry — the source-level free-run on `/local-compiled`
  (F191.5) already records the drain; per-image $0 rows add noise.
- Changing the cloud (non-localCompile) path — it keeps paid inline vision.
- Feeding embedded-image descriptions into the compile prompt — they remain
  separate accessibility/gallery artifacts (that's how cloud works today too).
- Auto-flag/quality-signal parity — cc writes the description; the F163.2
  auto-flag heuristic is a cloud-vision-rerun concern, left NULL for local.

## Architecture

```
Drop image / PDF (localCompile=true)
  │
  ├─ standalone image → extract parks it, content = "awaiting local vision" ($0, no Haiku)
  └─ PDF/docx → extract image rows (no LLM), vision-rerun job SKIPPED ($0)
  ▼
/local-ingest <tenant> <kb>   (interactive cc, $0)
  ├─ image source?  GET /raw → Read(/tmp/x.png) → describe → PUT /content
  ├─ GET /images?pending=1 → for each: GET bytes → Read → describe → POST /local-vision
  └─ compile source → Neurons  (as F191.2)
```

cc "sees" an image by downloading the bytes and Read-ing the local file (the
Read tool renders images), then describing them in its own turn — the same
$0 mechanism the whole F191 design rests on.

## Verification

- Standalone image + localCompile → upload returns $0 (extract_cost_cents=0,
  no vision model), content = the deferred marker, parked.
- PDF with embedded images + localCompile → no vision-rerun job queued; the
  `document_images` rows have `vision_description IS NULL`.
- `GET /images?pending=1` lists them; `POST .../local-vision` flips one to a
  description with `vision_model='claude-code'`, cost 0 (SQL round-trip proof +
  prod probe).
- Negative: same uploads WITHOUT localCompile still run paid cloud vision
  (unchanged).

## Rollout

1. Ship engine (`pnpm ship`) — gates + new endpoints. Additive, no migration
   (reuses existing `document_images` columns + `documents.content`).
2. Update the `/local-ingest` skill with the image step.
3. Drop a real image + a real PDF into the Station, run `/local-ingest`, confirm
   $0 descriptions land.
