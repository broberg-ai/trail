# F196.6 — trail-widget could not be built, and prod served a May image

**Status:** shipped · **Parent:** [F196](F196-deploy-self-report-upmetrics.md) · **Found:** 2026-08-29, while shipping F196.5

## Correction: this plan first blamed the symptoms

The first version said the defect was *four TS2339 errors* — `dispatchEvent` and
`shadowRoot` missing from `TrailChat` — and instructed whoever picked it up to
fix them "at the type level, not silenced".

That was wrong, and it was wrong for a reason worth leaving on the record: **I
read a truncated output.** The ship ran through `| tail -5`, so I saw the last
four error lines and carded those. The full compiler output has **six** errors,
and the two I never saw are the cause:

```
src/trail-chat.ts(27,69): error TS2307: Cannot find module 'lit' …
src/trail-chat.ts(28,48): error TS2307: Cannot find module 'lit/decorators.js' …
src/trail-chat.ts(88,10): error TS2339: Property 'dispatchEvent' does not exist …
   … and three more of the same
```

Without `lit`, `LitElement` is an error type, so every DOM member it supplies
looks missing. Four symptoms, one cause. Had anyone followed my original plan
they would have hand-declared `dispatchEvent` and `shadowRoot` onto a class that
was fine — shipping a widget whose element contract was a fiction, exactly what
the plan's own closing note warned against.

## The actual cause

```
node_modules/lit    -> ../../../node_modules/.pnpm/lit@3.3.3/node_modules/lit   (20 May)
node_modules/marked -> ../../../node_modules/.pnpm/marked@15.0.12/…            (20 May)
```

**Dangling symlinks.** `apps/widget` was once a pnpm workspace member; it is now
excluded (`!apps/widget` in `pnpm-workspace.yaml`) and installs with npm. A later
root install pruned the pnpm store, the link targets vanished, and the widget has
been unbuildable ever since — which is why production served
`trail-widget:deployment-01KRHYM9…` from May, an image predating the F196
self-report entirely. That is the whole reason it alone still answered
`no_release` while engine, admin and docs all reported `87212b3`.

Nothing was wrong with the code. The install was a ghost.

## Fix

`rm -rf node_modules package-lock.json && npm install` in `apps/widget`, and
commit the resulting lockfile — the app installs with npm, so its lockfile is a
real build input and belongs in the repo.

`marked` deserves its own sentence: the first `npm install` repaired `lit` but
left `marked` still pointing into the root pnpm store, where it happened to
still resolve. That is the identical trap one release from re-arming, so the
install was redone from scratch. Asserted afterwards: **zero symlinks** under
`apps/widget/node_modules`, and nothing resolving outside the app.

## Proof

Read off the running container and the register, not off the repo:

| | |
|---|---|
| `npm run build` | exit **0** (was 2) — captured, not piped |
| running image | no longer `deployment-01KRHYM9…` |
| release register | `widget.trailmem.com` → the shipped sha (was `no_release`) |

## The lesson, and it is the third time today

**A pipe discards every exit status but the last.** `pnpm ship:widget | tail -5`
reported `exited with code 0` — from `tail`. The build had failed four lines
earlier, and I was one step from reporting the widget as deployed. The same pipe
also cut the two error lines that held the cause, which is how the card came to
blame the symptoms.

So the rule has two halves, and today taught both: **when a command's exit code
is what you are about to report, do not pipe it — and when its output is what
you are about to diagnose from, do not truncate it.**
